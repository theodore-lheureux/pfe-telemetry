# Concurrent storage experiment

Run generated OTLP telemetry through the real ingestion service, Kafka and Parquet worker while independent DuckDB processes query historical measurements. Each scenario uses a new Compose project and named volumes. Existing telemetry and monitoring services keep running.

## Run

Requirements: Docker Compose, the repository's Python tooling, and enough free Docker memory for one additional pipeline and four query containers. Run from the repository root:

```sh
docker build --file tests/storage/Dockerfile --tag pfe-storage-experiment:local .
uv run --locked python tests/storage/run.py --output infra/telemetry/.state/storage-study --history 500 --batches 150 --interval-ms 100 --repeats 3
uv run --locked python tests/storage/summarize.py infra/telemetry/.state/storage-study
uv run --locked python -m unittest discover -s tests/storage -p 'test_*.py'
```

The Docker build runs the generator's validation test and existing storage tests on Linux. The workload uses only existing Rust dependencies and Python's standard library. Use a new output directory for every run; the runner refuses an existing directory. Its final component must be a lowercase Docker label of at most 36 characters.

For a functional smoke run, use `--history 10 --batches 10 --repeats 1`. Keep the first investigation within two focused working days: build and run the matrix on day one, then evaluate recovery and document the storage decision on day two. Stop expanding the matrix when a limitation has enough evidence to describe the next experiment.

## Workload and checks

Each deterministic batch contains 192 points: eight hosts, eight processes per host, two cumulative integer counters and one integer memory gauge. Values, timestamps and batch identities are reproducible. Measurement time advances one second per batch over a fixed historical interval; submission timestamps use the run's recorded wall-clock origin to satisfy ingestion's maximum submission age. This standard OTLP fixture exercises storage representation, rather than emulating the collector's full external profile or claiming physically realistic CPU values.

Each repetition runs these scenarios with a fresh 500-batch history:

1. One historical reader, no concurrent writes.
2. Concurrent writes, no historical readers.
3. Concurrent writes and one historical reader.
4. Concurrent writes and four historical readers.

The default load submits 150 further batches at ten batches per second. A reader cycles through a historical range aggregation, a whole-history aggregate, a filtered cumulative-counter rate query and a current-file freshness probe. Connections remain open throughout the phase. Historical results are checked against exact generated values; published data is checked for complete identities, duplicates and incorrect values before and after each phase. An unsuccessful query is recorded as a failure, not a zero-duration success.

The last scenario also checks writer exclusion, continued acceptance while the worker is stopped, catch-up, a worker `SIGKILL` during ingestion and restart of all three pipeline services. Finally, a new Kafka consumer group replays every batch into the existing files. This deliberately removes all consumer progress while preserving published measurements, exercising the replay case after publication without a checkpoint. It does not claim the timed `SIGKILL` lands in a particular filesystem instruction.

## Evidence and interpretation

The output directory contains:

- `events.jsonl`: commands and outputs, run parameters, acknowledgement times, SQL, query results and durations, resource samples, integrity checks and recovery events.
- `*.stderr`: DuckDB errors and container startup diagnostics.
- `summary.json`: per-scenario nearest-rank p50/p95/p99 distributions and sampled resource peaks, generated by `summarize.py`.
- `sources.json` and `override.json`: isolated source policy and Compose overrides. The random bearer token is passed through the environment and is not included in the event log.

Query wall times include pipe/CLI overhead but exclude container startup; DuckDB's `.timer` reports engine elapsed time separately with millisecond resolution. Acknowledgement timing measures the OTLP call through Kafka acceptance, not Parquet publication. Accepted rows per second uses the interval between first and last acknowledgement, excluding generator container startup.

Freshness measures the first sampled observation of the latest batch, relative to its acknowledgement. This is a sparse upper-bound observation for those batches, not a latency distribution for every point. Full-set checks establish eventual storage completeness. Docker resource samples are periodic observations rather than continuous maxima; block I/O counters include preloading and cache effects. The generator shares the Docker host with the pipeline and other running services.

The runner stops and removes its containers in cleanup and retains named volumes for inspection. It does not delete historical data automatically. An interrupted host process can leave containers behind; their names start with `pfe-storage-exp-` followed by the run directory name. Use the exact Compose commands recorded in `events.jsonl` to inspect or stop that project's services.

## Recorded run

The [2026-11-03 results](results/2026-11-03/) contain the completed 12-scenario run and recovery checks. See the [storage decision and measurements](../../docs/storage-experiment.md) for interpretation. `manifest.json` records source hashes and commands; `events.jsonl.gz` preserves the raw event log, and `query-stderr.txt.gz` preserves reader diagnostics.

Recompute the summary from the archived evidence without starting any services:

```sh
mkdir -p infra/telemetry/.state/storage-reanalysis
gzip -dc tests/storage/results/2026-11-03/events.jsonl.gz > infra/telemetry/.state/storage-reanalysis/events.jsonl
uv run --locked python tests/storage/summarize.py infra/telemetry/.state/storage-reanalysis
```
