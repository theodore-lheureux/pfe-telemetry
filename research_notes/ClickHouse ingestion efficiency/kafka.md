# ClickHouse Kafka and MergeTree tuning for Recount

## Which Kafka knobs deserve a benchmark?

### Takeaway

Keep one consumer for the hot stream. First reproduce the 16k→32k result on the 2-core-capped Oracle ARM profile with the 2-second flush unchanged. If the consumer is short of prefetched records despite a broker backlog, tune the queue and poll limits before adding concurrency.

### Cited findings

- Baseline supplied for this research: four shared ARM cores, ClickHouse capped at two, one hot-stream consumer across three skewed partitions, strict `ProtobufSingle`, 2-second flush, 16,384-row deployed block, about +6% throughput at 32,768 locally, and degradation with extra consumers. Those observations are not independently reproduced here. The **checked-in** renderer is different: recent `4096/1024` block/poll, one consumer and `kafka_thread_per_consumer=1`. Late is `64/32` for default `R=128`, with arbitrary event days. Retrieve effective DDL/settings for the benchmark rather than inferring them from either baseline — [Recount renderer](../../crates/telemetry-schema/src/ddl.rs), [deployment notes](../../infra/README.md).
- The rolling Kafka docs misleadingly call `kafka_max_block_size` a poll limit as well as describing a separate `kafka_poll_max_batch_size`. In the **pinned 26.8.34.13** source, `kafka_max_block_size` is passed to `KafkaSource` as its decoded row target; the local librdkafka `poll_batch` cap is `min(kafka_poll_max_batch_size, kafka_max_block_size)`. Source checks rows/time after draining the current poll. With one valid point per message, a source block may reach `block + effective_poll − 1` rows; a 2-second source time limit is not a bound on event visibility, write completion or commit. Preserve the worst-case late partition guard; recent data touches few days when first routed but exercise retained recent-topic backlog across day boundaries too — [pinned image](../../infra/clickhouse/Dockerfile), [Kafka settings docs](https://clickhouse.com/docs/engines/table-engines/integrations/kafka), [pinned StorageKafka batch getters](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L588-L605), [pinned KafkaSource loop](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/KafkaSource.cpp#L289-L327), [Recount late guard](../../infra/README.md).
- `kafka_poll_timeout_ms` is a local consumer wait; `fetch.wait.max.ms` is the broker's wait to satisfy `fetch.min.bytes`; `max.poll.interval.ms` is a group liveness limit between consume calls. The checked-in config sets broker fetch wait to 100 ms and `queued.min.messages=1`; the rollout's effective values still need checking. librdkafka describes the message target per topic+partition, with a higher-priority byte cap (high-level consumer queue across partitions), and a default fetch-queue backoff of 1 second when those thresholds are exceeded. Fetch byte caps and queue caps are not hard RSS bounds; keep the message cap/receive/headroom relationship intact. One local `poll_batch` need not correspond to one broker fetch — [pinned KafkaConsumer](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/KafkaConsumer.cpp#L441-L530), [librdkafka 2.12.1 settings](https://github.com/confluentinc/librdkafka/blob/v2.12.1/CONFIGURATION.md), [Recount Kafka config](../../infra/clickhouse/config.xml), [Recount byte derivation](../../infra/README.md).
- Concurrency spreads **partitions**, not one hot partition. `thread_per_consumer=1` starts one streaming task per consumer and flushes independently; with it disabled, one scheduled task reads multiple streams, not a guarantee of one equivalently sized part. Pinned code sets pipeline thread count to stream count (one in the current mode); server `max_threads` is not a multiplier for this parser. More consumers can leave the bottleneck unchanged and create smaller parts, extra writes/merges and quota pressure. Altinity also notes the partition and pool prerequisites; its advice is not a throughput estimate for this host — [Kafka docs](https://clickhouse.com/docs/engines/table-engines/integrations/kafka), [task creation](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L214-L224), [stream pipeline](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L729-L775), [Altinity parallel consumption](https://kb.altinity.com/altinity-kb-integrations/altinity-kb-kafka/02-consumption-patterns/altinity-kb-kafka-parallel-consuming/).

### Inferences

1. **Priority 1 — recent-stream block size, at fixed poll cap and flush.** Compare 16k and 32k under backlog and realistic live load, keeping one consumer, 2 seconds, durability, readers and views identical. Fewer parts and commits per point should amortize fixed costs _if actual flushes get larger_. At uniform arrival, filling within two seconds would require roughly 8.2k/s and 16.4k/s for those targets respectively, before considering prefetch, read stalls or processing. If both usually time-flush to the same size, a larger target is unlikely to improve the ordinary path. Stop at 32k unless actual batch histograms, merge/part improvement and memory headroom make the case for another step. General advice to use 10k–100k rows is for synchronous push inserts, not a universal Kafka or memory target — [ClickHouse insert strategy](https://clickhouse.com/docs/best-practices/selecting-an-insert-strategy#batch-inserts-if-synchronous), [pinned flush/commit path](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L742-L776).
2. **Priority 2 — poll/prefetch, conditional on underfill.** At fixed block and flush, compare the effective recent poll cap to a modest increase (e.g. 1,024→2,048 if measured polls are often full); it can reduce call overhead but does not make protobuf decoding columnar or increase disk efficiency by itself. If sustained backlog coexists with small/empty polls, inspect librdkafka fetch sizes, queue occupancy and backoff first. If the rollout retains `queued.min.messages=1`, try a bounded higher message target while holding the byte cap, then retest at sparse rates; if the byte cap is already binding, only consider a small, memory-budgeted increase when justified by fetch starvation. If requests are plentiful but predominantly tiny, a modest topic-scoped `fetch.min.bytes` can coalesce them at the cost of sparse latency; keep the current fetch wait initially. Adjust `kafka_poll_timeout_ms` only if sparse waits/empty-poll overhead show a problem; don't blindly drop it to near zero or conflate it with broker wait. Optimize late separately only within its existing guard — [librdkafka settings](https://github.com/confluentinc/librdkafka/blob/v2.12.1/CONFIGURATION.md), [KafkaSource loop](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/KafkaSource.cpp#L289-L327).
3. **Trigger-based — schedule contention, not more hot consumers.** Repo config has two message-broker slots, and besides recent/late the participant stream can be attached. Count _active attached tasks_ and look for long runnable gaps, revocations and `MAXPOLL`, not merely occupancy. If three tasks really compete for two slots and CPU has headroom or poll waits hog slots, benchmark a single extra broker slot with reader and merge load present. If backlog cycles repeatedly pause despite headroom, check source logs for stall/work-duration reschedules before testing a shorter `kafka_consumer_reschedule_ms`; faster empty/error retries can spend more CPU. Raising `max.poll.interval.ms` is only a reliability mitigation for verified long processing, not a throughput optimization, and delays detection of a stuck consumer. Don't enlarge all pools, repartition/rekey to fight skew, or lift the cap as a tuning result — [Recount pool config](../../infra/clickhouse/config.xml), [participant stream](../../infra/clickhouse/participants.sql.in), [pinned rescheduling](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L630-L689), [Altinity scheduling field report and metrics](https://kb.altinity.com/altinity-kb-integrations/altinity-kb-kafka/04-operations-troubleshooting/background_message_broker_schedule_pool_size/).

### Gaps

- Effective deployed poll/queue/flush settings, current image digest, partition rates, actual part/flush sizes, and cause of the local +6% and multi-consumer regression were not supplied. No matching published ARM/shared-quota/strict-protobuf benchmark was found. No benchmark was run.

## Which MergeTree changes can lower work without changing results?

### Takeaway

Keep the event-day partition, full `ORDER BY`, `ReplacingMergeTree`, and both fsync settings. A reversible, isolated test of coarser granularity or a targeted lossless codec is more promising than changing ordering or adding asynchronous buffering. Profile first: Recount does more than parse protobuf and write one table.

### Cited findings

- A part is sorted, indexed, compressed and written; every touched table partition can create a new part from a block. In pinned code, the insert writer tests for ordering before computing a stable sorting permutation; `MergeTreeDataWriterSortingBlocksMicroseconds` and `MergeTreeDataWriterBlocksAlreadySorted` are explicit counters. The writer uses the fsync setting for finalization and constructs a directory sync guard for `fsync_part_directory` — [ClickHouse parts](https://clickhouse.com/docs/parts), [sort/profile counters](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/MergeTree/MergeTreeDataWriter.cpp#L788-L812), [directory sync](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/MergeTree/MergeTreeDataWriter.cpp#L971-L979), [fsync finalization](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/MergeTree/MergeTreeDataWriter.cpp#L1088-L1099).
- The point table materializes `series_id` from sorted/filtered nested attributes; three downstream incremental discovery MVs group metric definitions and expand point/resource attributes. Their target writes and merges are real work even though they do not add another point delivery hop. Include these in a qualifying benchmark, and profile the pipeline before attributing all CPU to protobuf, the sort or disk compression — [Recount DDL](../../infra/clickhouse/schema.sql.in).
- Replacement identity is the full `ORDER BY`, **not** sparse `PRIMARY KEY`; without `ver` the latest row in selection wins. Background replacement is eventual; Recount uses `FINAL` for duplicate-sensitive reads. The pinned default row granularity is 8,192, versus Recount's 256; an adaptive byte cap also limits granules. A coarser granule cuts marks/index entries when the row cap is binding, but can read more unrelated rows, especially for selective queries — [ReplacingMergeTree docs](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree), [pinned granularity settings](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/MergeTree/MergeTreeSettings.cpp#L1808-L1835), [Recount DDL and query guidance](../../infra/README.md).
- Disk codecs are distinct from Kafka producer compression and Native/HTTP transport compression. Pinned insert chooses table/default compression separately from per-column codec definitions; in the absence of a table default, server compression rules apply. The normalizer explicitly requests Kafka Zstd; check effective topic policy and stored batch codec before using that as baseline. ClickHouse's codec examples show data locality matters (e.g. Delta for a sequence ordered together); Altinity's format comparisons used plain synthetic `Engine=Null` and **did not** measure protobuf, fsync or MergeTree — [pinned part codec selection](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/MergeTree/MergeTreeData.cpp#L10286-L10314), [ClickHouse on-disk compression](https://clickhouse.com/docs/data-compression/compression-in-clickhouse), [normalizer producer](../../apps/normalizer/src/runtime.rs), [Altinity synthetic parsing comparison](https://kb.altinity.com/altinity-kb-schema-design/ingestion-performance-and-formats/).

### Inferences

4. **Priority 3 — index granularity and part format (separate tests).** Start at 256 versus 512/1,024 with identical sorting/partition/replacement keys, using fresh disposable tables so mixed old/new parts don't confound results. Confirm marks and index bytes per point actually fall. Judge on CPU/point and write amplification **plus** production-like narrow project/time/series `FINAL` read bytes and p95/p99. Consider a strict prefix sparse `PRIMARY KEY` only if marks/index show material overhead and query tests can absorb lost pruning; do not truncate `ORDER BY`. If the batch A/B crosses the Compact/Wide threshold and fsync/file fan-out is material, compare part types under the same durability and track read and merge costs; first inspect part type/rows/bytes rather than forcing a global threshold. The pinned settings expose row and byte Wide thresholds — [settings source](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/MergeTree/MergeTreeSettings.cpp#L72-L88), [system.parts](https://clickhouse.com/docs/operations/system-tables/parts).
5. **Priority 4 — targeted, lossless codecs only if the profile supports it.** For compression CPU, compare the effective on-disk codec to LZ4 on the heaviest columns that are not already using it. For disk/write amplification, try `ZSTD(1)` versus LZ4 on highly compressible columns, or `Delta, LZ4` on timestamp columns _only if_ measured in-part adjacent values justify it; this order sorts time within series prefixes, not globally. Measure compression/decompression CPU, merge cost and retained bytes/point, not only fresh-part size. Do not blindly add high-level Zstd, Gorilla/DoubleDelta across irregular mixed series, or `NONE` globally. If Kafka decompression dominates instead, a separate end-to-end producer Zstd→LZ4 trial may move CPU across services and increase broker bytes, shrinking the effective byte-limited replay window unless retention headroom is verified. Changing `kafka_compression_codec` on a table is for producing, not consuming — [compression guidance](https://clickhouse.com/docs/data-compression/compression-in-clickhouse), [Kafka settings](https://clickhouse.com/docs/engines/table-engines/integrations/kafka), [Recount retention guide](../../docs/kafka-recovery.md).
6. **Low / profile-triggered — sorting and merges.** Use `AlreadySorted`/sort time before investigating upstream ordering. Per-request sorting doesn't guarantee full-key order in ClickHouse blocks mixed from three skewed Kafka partitions, and SQL `ORDER BY` in the MV generally moves the sort rather than eliminating it. Do not reorder actual emissions/replay in this study; relative order matters for conflicting equal keys. A storage-only presorted-copy experiment can bound potential sort cost but cannot qualify full ingestion. If merge profiles show per-block overhead and safe RSS headroom, independently compare the repo's intentionally small merge target (128 rows/1 MiB) with a modest increase, under wide attributes; larger blocks trade memory for potentially less per-block work. If merge concurrency is causing quota throttling or read tail spikes, a controlled reduction is worth testing only if parts still stabilize. Don't disable merges, schedule routine `OPTIMIZE FINAL`, increase merge pools blindly, or benchmark only before merge debt appears — [ClickHouse pre-sort caveat](https://clickhouse.com/docs/best-practices/selecting-an-insert-strategy#pre-sort-if-low-cost), [Replace winner rule](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree), [Recount merge limits](../../infra/clickhouse/config.xml), [pinned merge block sizing](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/MergeTree/MergeTreeSettings.cpp#L456-L473).

### Gaps

- No measured profile splits decode/decompression, nested transformations, discovery views, sort, compression, fsync and merges in this workload. Effective adaptive granularity, per-column codecs, part formats, write/fsync costs, and the reader regression budget need direct measurement.

## How should capacity, CPU per point and replay safety be judged?

### Takeaway

Measure matched-rate CPU per unique durable point and max sustainable throughput separately. Qualify only configurations whose per-partition lag and MergeTree part debt stabilize, with the same points, query results, latency and crash/replay behavior.

### Cited findings

- The pinned native Kafka engine builds a synchronous dependency-view insert (`async_insert=false`, `no_squash=true` at the interpreter), executes its pipeline, and only then calls the source commits. Kafka offset and ClickHouse storage are not transactional: a crash between successful storage and broker commit may replay already-written points. Recount disables intermediate commits, direct select commits, automatic commit/store, and parse skips/errors; `FINAL` gives logical uniqueness, not exactly-once physical insertion. Do not assume identical replay block boundaries or independent deduplication of every MV — [pinned pipeline and commit](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L708-L776), [Recount renderer](../../crates/telemetry-schema/src/ddl.rs), [Recount Kafka config](../../infra/clickhouse/config.xml), [recovery guide](../../docs/kafka-recovery.md).
- Broker committed offsets and high watermarks show recovery progress; `system.kafka_consumers` exposes current offsets, polls, messages read, exceptions, rebalance counts and optional librdkafka stats. Current offset is not itself broker-committed proof. A time retention ceiling and per-partition byte ceiling both apply; a hot partition can expire the unread prefix first. The runtime cgroup exposes actual CPU usage and throttling separately (`cpu.stat`, `cpu.max`) — [ClickHouse consumer metrics](https://clickhouse.com/docs/operations/system-tables/kafka_consumers), [Recount recovery](../../docs/kafka-recovery.md), [Linux cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#cpu).

### Inferences

- **Three test regimes.** Re-run at (1) fixed realistic offered rates including sparse/bursty ingestion and representative readers, (2) a step-rate test to find the highest rate with no persistent per-partition lag or active-parts/merge-debt growth, (3) finite preloaded backlog catch-up at the same cap, separately with continued live traffic and a late-day replay fixture. Run long enough for merges, use repeated paired variants on Oracle ARM with comparable neighboring load, and retain the same finite input offset ranges, point widths (including extremes), skew, day mix, readers, both fsync settings, all views and memory limits. Report headroom of the hottest partition, not just aggregate rows/s. If live arrivals are λ and stable durable processing is μ, an existing backlog only clears if μ>λ; rough catch-up time is backlog/(μ−λ) for a stable rate, evaluated per binding partition and against retained earliest — [parts lifecycle](https://clickhouse.com/docs/parts), [Recount retention/recovery](../../docs/kafka-recovery.md).
- **Two distinct metrics.** CPU efficiency = delta ClickHouse cgroup CPU seconds / expected unique source points durably materialized and verified in that interval (report CPU µs/point), at matched rate with merge work accounted for or an equal drain window; separately record total stack CPU/point so a gain shifted to Kafka/normalizer is visible. Capacity = durable, stable points per wall second at the same effective quota and latency. +6% wall throughput is not +6% CPU efficiency. One source lane can be saturated while aggregate CPU is below two cores; low CPU plus high I/O wait or empty poll evidence indicates a different bottleneck. Track quota throttling, host contention and I/O wait, process/thread/profile CPU where available, peak RSS, actual rows and bytes per flush/part, commits and lags per partition, `NewPart` and `MergeParts` bytes/counts (if logged), active part trends, disk bytes/fsync tail, visibility/reader tails, and broker/normalizer resource use. Background settings and observability should be identical between matched variants; heavy profiling only in separate diagnostic runs — [cgroup CPU accounting](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#cpu), [consumer counters](https://clickhouse.com/docs/operations/system-tables/kafka_consumers), [Altinity part-log ingestion measurement](https://kb.altinity.com/altinity-kb-useful-queries/ingestion-rate-part_log/), [Recount logging config](../../infra/clickhouse/config.xml).
- **Recovery gates on disposable data only.** Compare expected full keys and value-content against `FINAL`, not just counts or physical rows; test sparse tail, wide records, day boundaries, arbitrary-day late input and duplicate/conflicting-key cases under the existing winner contract. Test crash before write completes and ambiguous loss of the Kafka commit after successful write, advance only through successful durable writes, restart on the same isolated group, confirm effective offset recovery, no missing sample or discovery outputs, and no unnoticed errors. Preserve Kafka group/reset policy, record framing, routing/affinity, no-skip policy, fsync, partition guard, replacement identity and reader semantics. A replay delay or larger batch may change the number of physical duplicates after a crash; it must not lose points or silently alter logical results — [pinned commit ordering](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L757-L776), [ReplacingMergeTree winner rules](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree), [Recount recovery guide](../../docs/kafka-recovery.md).
- **Do not try within scope:** skip broken records, turn parse failures into committed DLQ/drop paths, commit per poll or on SELECT, weaken fsync, add an in-memory Buffer/fire-and-forget path, enable `materialized_views_ignore_errors`, substitute plain MergeTree, change dedup keys, or move to Keeper offsets (different checkpoint authority). Native Kafka explicitly uses the synchronous pipeline; general advice to enable client `async_insert` is not a relevant knob. Also defer new wire formats, multi-point Kafka records, offset-store redesign, and upstream rekeying: they change the replay/record contract or architecture rather than tuning existing ingest. No production changes or live offset manipulation are implied — [Kafka docs, including Keeper](https://clickhouse.com/docs/engines/table-engines/integrations/kafka), [pinned pipeline](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L718-L727), [async insert durability modes](https://clickhouse.com/docs/best-practices/selecting-an-insert-strategy#choosing-a-return-mode), [Recount contract](../../infra/README.md).

### Gaps

- No matched-load production CPU/point, steady part creation/merge rate, reader/visibility SLO, event-day distribution, retention headroom under skew, or episode of observed quota versus device saturation was supplied. The local +6% is a reason to test, not a capacity or savings projection.
