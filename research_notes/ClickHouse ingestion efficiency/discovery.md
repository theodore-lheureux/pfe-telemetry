# Reducing ClickHouse discovery CPU without losing catalog entries

## What must stay exact, and where does discovery cost occur?

### Takeaway

Keep all points and optimize discovery independently. Compare the complete grouped catalogs at nanosecond precision, not the limited web responses.

### Cited Findings

- Both Kafka paths insert into `metric_points`; two attribute views and one metric view then run on its inserted blocks. The source uses `ReplacingMergeTree`, partitioned by event day, and separately computes the materialized `series_id`. The comment about discovery adding “no ingestion write path” means no separate producer route, not no synchronous CPU or catalog writes. Normal successful inserts update dependent views, but intermediate visibility across tables is not atomic. — [Schema](../../infra/clickhouse/schema.sql.in#L3), [ClickHouse insert synchrony](https://clickhouse.com/docs/knowledgebase/are_materialized_views_inserted_asynchronously), [incremental views](https://clickhouse.com/docs/materialized-view/incremental-materialized-view)
- The exact attribute key is `(project_id, metric_name, scope, attribute_key, value_kind)` with `max(time_unix_nano)`. Preserve kinds 2–6, only top-level scalar paths, point/resource separation, and the scope-specific continuity-marker exclusions. Strip only the first slash; `~0` and `~1` escapes survive. A literal slash inside an input key is escaped, while a nested path has a structural `/`. Scope attributes are not part of today's catalog. Metric variants are keyed by `(project_id, metric_name, metric_kind, temporality, monotonic_state, unit)`, with unknown monotonicity encoded as `2`, exact `min`/`max` event times and `anyLast(description)`. — [Catalog DDL](../../infra/clickhouse/schema.sql.in#L64), [attribute projection](../../crates/telemetry-schema/src/projection.rs#L13)
- `anyLast` is nondeterministic, not the description on the point with the latest timestamp. A rewrite can change the selected description even with identical variant rows and event times. Switching to `argMax` would be a separate product decision; a timestamp-only argument still leaves equal-time ties unspecified. The app also has no tie-breaker in its choice of latest metric variant when timestamps tie. — [`anyLast`](https://clickhouse.com/docs/sql-reference/aggregate-functions/reference/anylast), [`argMax`](https://clickhouse.com/docs/sql-reference/aggregate-functions/reference/argmax), [metric reads](../../apps/web/src/analytics/discovery.server.ts#L49)
- `AggregatingMergeTree` combines equal sorting keys within merges, not necessarily across every visible part. Keep reader grouping and `max`/`min`; their partial results are sufficient (`max(max(A), max(B)) = max(A ∪ B)`). The web catalog collapses dimensions for some endpoints, caps output and metric lists, and converts nanoseconds to millisecond dates. Its sampled example/value endpoints are separate from discovery and still need point data. — [AggregatingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/aggregatingmergetree), [SimpleAggregateFunction](https://clickhouse.com/docs/sql-reference/data-types/simpleaggregatefunction), [web discovery reads](../../apps/web/src/analytics/discovery.server.ts#L100)

### Inferences

- Use the current insert-trigger catalog as the reference for “ever sent.” An older late point may introduce a key/variant or lower metric `first_seen`, and must not move an existing `last_seen` backward. `min` and `max` tolerate reprocessing identical inputs. If two rows share a replacing key but disagree about discoverable data, historical incremental views see both while later raw scans may see only the survivor. Do not use `FINAL` as a discovery optimization or assume a raw-table rebuild necessarily reconstructs the ever-sent catalog. — [Source schema](../../infra/clickhouse/schema.sql.in#L23), [ReplacingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree), [CREATE VIEW semantics](https://clickhouse.com/docs/sql-reference/statements/create/view)
- Test bidirectional set differences between full grouped results for identical input, including variant first/last times. Include empty arrays; nested versus escaped paths; bytes; reserved markers; same key across projects, metrics, scopes and types; exact retries; an old arrival with a new key/variant; a late arrival with an event time greater than the last time for that specific key; and out-of-order metric first-seen changes. Check the point stream/storage separately. For description, document the existing nondeterminism and test fixed-description fixtures exactly. — [Catalog DDL](../../infra/clickhouse/schema.sql.in#L64), [web discovery reads](../../apps/web/src/analytics/discovery.server.ts#L49), [`anyLast`](https://clickhouse.com/docs/sql-reference/aggregate-functions/reference/anylast)

### Gaps

- Assignment-supplied local results: per-row dedup with sorting before `ARRAY JOIN` was about 7% slower with about 2% more CPU; removing all discovery increased throughput about 23% with only about a 5% CPU change. No underlying profile, variance or CPU denominator was supplied. The throughput delta is not evidence that discovery consumes 23% of CPU, nor a forecast of what an exact rewrite will recover.

## Which SQL and batching experiments should run first?

### Takeaway

Benchmark narrow, early filtering in the existing attribute views before changing architecture. Keep metric discovery unless profiling shows a meaningful share of the cost.

### Cited Findings

- `ARRAY JOIN` expands arrays into rows and drops empty arrays in its non-`LEFT` form. `arrayFilter` and `arrayMap` allow reduction before expansion. The 26.8 source already has lazy replication support; the additional optimization for wide non-expanded columns in PR #124727 was merged for 26.10, not the repo-pinned 26.8 image. Inspect what is already pruned instead of assuming wide payload columns are copied. — [ARRAY JOIN](https://clickhouse.com/docs/sql-reference/statements/select/array-join), [array functions](https://clickhouse.com/docs/sql-reference/functions/array-functions), [26.8 ArrayJoinAction](https://raw.githubusercontent.com/ClickHouse/ClickHouse/26.8/src/Interpreters/ArrayJoinAction.cpp), [PR #124727](https://github.com/ClickHouse/ClickHouse/pull/124727), [pinned image](../../infra/clickhouse/Dockerfile#L1)
- Grouping uses specialized hash tables selected for the key types and workload. `LowCardinality` dictionary-encodes strings, with diminishing or negative returns at high distinct counts. Kafka has independent poll, block and flush controls; this repo uses a recent block target of 4,096, with a smaller late lane bounded by partition safety. — [ClickHouse grouping internals](https://clickhouse.com/blog/clickhouse-group-by-parallel-replicas-8900-cores), [LowCardinality](https://clickhouse.com/docs/sql-reference/data-types/lowcardinality), [Kafka engine](https://clickhouse.com/docs/engines/table-engines/integrations/kafka), [batching implementation](../../crates/telemetry-schema/src/ddl.rs#L66)

### Inferences

1. **Isolate the expensive stage.** Benchmark the baseline and omit each discovery view individually in disposable profiling runs only; retain the no-discovery run as a ceiling on this fixture. Compare CPU time per accepted point, sustained points/s, lag, catalog latency, memory, target parts/merges and I/O. Compare matched load as well as saturation; use `system.query_views_log` where enabled (per-view duration, rows, `ProfileEvents`), `system.query_log`, and `system.part_log`. Check `EXPLAIN`/pipeline for columns carried through expansion. — [View log](https://clickhouse.com/docs/operations/system-tables/query_views_log), [query log](https://clickhouse.com/docs/operations/system-tables/query_log), [part log](https://clickhouse.com/docs/operations/system-tables/part_log), [EXPLAIN](https://clickhouse.com/docs/sql-reference/statements/explain)
2. **Narrow and filter before unfolding; benchmark the pieces separately.** Feed only path/kind subcolumns into discovery where the analyzer allows it; filter kind, nesting and reserved paths before expanding when there is a material rejection rate. If almost every node qualifies, the filter/map array allocations could cost more than they save. On validated slash-prefixed paths, `position(path, '/', 2) = 0` checks for a structural slash without materializing `substring(path, 2)` for the predicate. Group on the unchanged path and strip the prefix after aggregation, subject to checking equivalence on admissible data and plan placement. In the separate views, scope is constant: project it but do not require it as an input to aggregation. Do not add per-row sorting or distinct by default; the input validates duplicate map keys and exact `max` is already duplicate-safe. — [String search functions](https://clickhouse.com/docs/sql-reference/functions/string-search-functions#position), [array functions](https://clickhouse.com/docs/sql-reference/functions/array-functions), [duplicate validation](../../crates/telemetry-schema/src/identity.rs#L204), [catalog DDL](../../infra/clickhouse/schema.sql.in#L108)
3. **Test one attribute view, then larger recent batches, independently.** Tag qualifying entries with scope, concatenate point/resource arrays, expand once, group by the full exact key. This can eliminate one query/target insert per block, but not the need to process each eligible entry, and concat/tagging can outweigh the savings. Two separate expansion calls can form a product; multi-array `ARRAY JOIN` pairs positions, not scopes, so neither substitutes for tagged concatenation. Test larger recent blocks if profiling implicates fixed insert/part costs; monitor flush delay and memory. Do not blindly raise the late limit: a late block can hit as many day partitions as it has points, and a poll can overshoot the nominal row target. — [ARRAY JOIN](https://clickhouse.com/docs/sql-reference/statements/select/array-join), [Kafka engine](https://clickhouse.com/docs/engines/table-engines/integrations/kafka), [batching implementation](../../crates/telemetry-schema/src/ddl.rs#L85), [ClickHouse MV engineering guidance](https://clickhouse.com/blog/using-materialized-views-in-clickhouse)
4. **Conditional: factor repeated attribute sets across rows, especially resource attributes.** On one block, first group by project/metric and the _full ordered array_ of eligible `(path, kind)` pairs with partial max time. Expand the surviving arrays and group again by the ordinary attribute key. Exact by distributivity of max: order differences reduce collapse, not correctness. No sort or hash-only identity is needed; `series_id`/`resource_id` alone would need a proof that no catalog entry can vary within the group (and a finite hash cannot guarantee equality). Use only when distinct projected arrays are a small fraction of rows; hashing arrays and a second grouping can cost more. Try compact scope or `LowCardinality` changes only when profiling implicates key hashing or writes; changing only the target type does not automatically change the MV query's grouping key types. — [Grouping internals](https://clickhouse.com/blog/clickhouse-group-by-parallel-replicas-8900-cores), [SimpleAggregateFunction](https://clickhouse.com/docs/sql-reference/data-types/simpleaggregatefunction), [LowCardinality](https://clickhouse.com/docs/sql-reference/data-types/lowcardinality), [source identity](../../infra/clickhouse/schema.sql.in#L6)

### Gaps

- No SQL rewrite has been benchmarked here. Unknowns include eligible/ineligible node ratio, path/kind subcolumn pruning on the actual pin, resource-array repetition within batches, and how much of the observed throughput difference is view compute versus target insert/merge scheduling.

## When is asynchronous discovery worth the freshness trade-off?

### Takeaway

If ingestion headroom is more important than immediate catalog visibility, batch only newly arrived data using a durable arrival cursor. Use a full refresh only when the retained source is small or a full reconciliation is intentionally budgeted.

### Cited Findings

- Standard refreshable views are not insert triggers. `REFRESH EVERY`/`AFTER` runs the query periodically; without `APPEND` the result replaces the previous contents atomically per view. Ordinary `APPEND` does not make the scan incremental. Refresh slots can be missed when work runs long, and failures/restarts can extend staleness. `system.view_refreshes` exposes status and timestamps. — [Refreshable views](https://clickhouse.com/docs/materialized-view/refreshable-materialized-view), [CREATE VIEW scheduling and retries](https://clickhouse.com/docs/sql-reference/statements/create/view#refreshable-materialized-view)
- The rolling documentation also lists `APPEND INCREMENTAL`, introduced in **26.9**, unavailable on this repo's 26.8 pin. Current docs require a single plain `MergeTree` source with block-number/block-offset columns enabled and reject joins, unions and subqueries. This is not a drop-in option on `metric_points` (`ReplacingMergeTree`). The ClickHouse restart note also warns of cursor loss/replay for uncoordinated incremental refreshes without a transactional target that committed the cursor. — [26.9 release](https://clickhouse.com/blog/clickhouse-release-26-09#incremental-refreshable-materialized-views), [CREATE VIEW restrictions](https://clickhouse.com/docs/sql-reference/statements/create/view#refreshable-materialized-view), [restart behavior](https://clickhouse.com/docs/resources/support-center/knowledge-base/materialized-views/what-happens-to-refreshable-materialized-views-when-the-server-restarts), [pinned image](../../infra/clickhouse/Dockerfile#L1)

### Inferences

- **Preferred asynchronous candidate: arrival-based microbatches.** Prototype a durable lightweight staging stream/table or independent consumer with cursors per topic/partition for **both** recent and late input. Stage only discovery data if possible; project/group in larger batches and append partial states into the existing catalog targets. Commit checkpoints only after all output sinks are confirmed; replay after partial failure safely for key presence/min/max. Keep a complete historical baseline or replay a complete input before declaring catch-up. Track arrival-to-catalog lag and checkpoint coverage, including outages and source retention. An independent consumer can publish discovery before the corresponding point is queryable; if that is unacceptable, tie discovery to successful point insertion via a durable staging path. Additional staging writes or decoding can consume the apparent CPU gain, so measure whole-system CPU and live contention, not just INSERT duration. — [Kafka engine and offsets](https://clickhouse.com/docs/engines/table-engines/integrations/kafka), [incremental view mechanics](https://clickhouse.com/docs/materialized-view/incremental-materialized-view), [partial aggregate values](https://clickhouse.com/docs/sql-reference/data-types/simpleaggregatefunction)
- **Alternative: refresh dirty event-day partitions, not a fixed event-time lookback.** Durably record which days received new arrivals and consume dirty generations without racing arrivals during a scan; preserve existing extrema and append newly computed maxima/minima. Works as a lower-complexity reconciliation mechanism if days have bounded scan cost and retained rows are sufficient. Old sparse arrivals can cause expensive rescans; reprocessing an old day cannot reconstruct rows already replaced/dropped. A wall-clock ingestion timestamp alone is not a committed-order checkpoint; a fixed event-time lookback cannot discover an unseen value in a late day outside the window. — [event-day partitioning](../../infra/clickhouse/schema.sql.in#L23), [ReplacingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree), [SimpleAggregateFunction](https://clickhouse.com/docs/sql-reference/data-types/simpleaggregatefunction)
- **Lowest architecture effort, highest growing scan cost: full refresh.** Prefer an atomic replacement view over ordinary APPEND for small complete retained input or a compact staging/summary source. This moves work off insert but may increase total I/O/CPU as history grows. It catches late points of any age present at the next successful scan, but cannot promise the ever-sent catalog if input has expired or nonidentical duplicate-key rows were replaced. Two refreshed catalog tables also need explicit coordination if one snapshot across them is required. Refreshing only the compact catalog may reduce read/merge work but does not remove the original expansion cost while the incremental attribute views are still active. — [Refreshable views](https://clickhouse.com/docs/materialized-view/refreshable-materialized-view), [ReplacingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree)

### Gaps

- No discovery freshness SLO, maximum replay outage, or verified proof of lossless raw-table reconstruction was supplied. Determine these before selecting a scheduled architecture. This is a research comparison, not a proposal to migrate a discarded prototype schema or to change the deployed ClickHouse version.
