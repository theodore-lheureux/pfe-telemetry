# Kafka-to-MergeTree ingest CPU and structural alternatives

## How much CPU does each accepted point cost?

### Takeaway

Use process or cgroup CPU per verified point as the budget, then attribute it with controlled replays, CPU stacks and system logs. Dashboard latency, insert latency, materialized-view duration and merge duration are not interchangeable with CPU time.

### Cited Findings

- Recount pins ClickHouse `26.8.34.13` and inserts one bare `AnalyticalPoint` per Kafka record with `ProtobufSingle`; many records already form one ClickHouse block. Recent and late topics each have a pass-through view into `metric_points`. That `ReplacingMergeTree` computes `series_id`, partitions by `event_day`, sets index granularity to 256, and enables both part and directory fsync. Three further incremental views write metric definitions and point/resource attribute definitions. The DDL comment about discovery adding “no ingestion write path” should not be read as “no additional work”: the views group or expand attributes and write aggregate table parts. — [Point contract](../../docs/telemetry-point-contract.md), [DDL](../../infra/clickhouse/schema.sql.in), [Incremental materialized views](https://clickhouse.com/docs/materialized-view/incremental-materialized-view)
- `system.query_log` exposes query identity/type, rows, elapsed time and `ProfileEvents`; `query_thread_log` can break down attributed threads. Sum `UserTimeMicroseconds` and `SystemTimeMicroseconds` for CPU where present, not `query_duration_ms`, `RealTimeMicroseconds` or disk elapsed counters. `query_views_log` needs the server log and `log_query_views=1`; use view names, statuses, timings, input/output counts, `initial_query_id` and available events to locate work. CPU counters may be absent; missing is not zero. Parent inserts, nested views and thread breakdowns are overlapping attribution, not additive budgets. — [Query log](https://clickhouse.com/docs/reference/system-tables/query_log), [Thread log](https://clickhouse.com/docs/reference/system-tables/query_thread_log), [View log](https://clickhouse.com/docs/reference/system-tables/query_views_log), [Pinned event definitions](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Common/ProfileEvents.cpp)
- `EXPLAIN PIPELINE` shows the processor graph for a suitable query; with `log_processors_profiles=1`, `processors_profile_log` shows processor elapsed, input/output waits and row/byte flow. The docs' `sleep(1)` example records ~1 s of processor elapsed without ~1 s of CPU. Run it on equivalent **foreground** lab workloads (e.g., view `SELECT` logic over a replay block), not a live Kafka table. In the pinned code, `StorageKafka::streamToViews` constructs an internal `InterpreterInsertQuery`, completes it with `KafkaSource`, runs the completed pipeline, then commits; it doesn't take the ordinary client `executeQuery` path. The pipeline profiler is gated on a process-list element. Verify coverage with a known batch; don't assume that enabling a client setting profiles the background consumer or that a missing query ID means no work. — [Processor log](https://clickhouse.com/docs/reference/system-tables/processors_profile_log), [Pinned Kafka path](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L693-L780), [Pinned pipeline executor](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Processors/Executors/PipelineExecutor.cpp)
- CPU traces in `trace_log` sample on CPU time; `Real` samples are wall time and include waits. Correlate by thread name/ID, query ID when attached, and timestamps; resolve against the matching binary (verify actual columns and symbols on 26.8, rather than assuming rolling-doc examples apply). For uncovered Kafka/librdkafka or merge workers, use Linux process-wide on-CPU sampling in a permitted lab (e.g., `perf` with call graphs and suitable unwinding/symbols); align the window with Linux `cpu.stat` `usage_usec` and check throttling. CPU sample fractions reflect on-CPU composition, not individual stage timers. — [Sampling query profiler](https://clickhouse.com/docs/concepts/features/performance/troubleshoot/sampling-query-profiler), [Trace log](https://clickhouse.com/docs/reference/system-tables/trace_log), [perf record](https://man7.org/linux/man-pages/man1/perf-record.1.html), [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)
- Per-partition `part_log` differentiates `NewPart` from completed `MergeParts`, with rows, disk bytes, merge input rows/bytes, error and operation events. `system.merges` is an in-flight snapshot, **not** a pending queue length; track active-part trend in `system.parts` and use merge-work/drain windows. Check for CPU keys in completed part events; even the docs' example shows only elapsed counters for CPU-adjacent timing. `system.kafka_consumers` exposes assignments/offsets, commit/rebalance data and exceptions; compare with broker log-end and committed offsets per partition rather than interpreting an in-process current offset as durable/queryable. — [Part log](https://clickhouse.com/docs/reference/system-tables/part_log), [Merges](https://clickhouse.com/docs/reference/system-tables/merges), [Parts](https://clickhouse.com/docs/reference/system-tables/parts), [Kafka consumers](https://clickhouse.com/docs/reference/system-tables/kafka_consumers)

### Inferences

1. **Establish the denominator.** Replay a manifest with expected logical point identities and payloads (counts per lane/day/identity cohort, optionally exact fixture equality). Compare raw attempt/physical counts and logical point results under the application's existing dedup semantics. Never use `system.events.InsertedRows`, `sum(part_log.rows)` across all targets, view-output rows or committed offsets as unique point count. For equal verified work, `CPU µs/point = Δusage_usec / verified logical points`; report gross and incremental versus matched idle/read-only controls. If ClickHouse sustained exactly two fully busy cores during 10.3k verified points/s, that is about **194 combined CPU µs/point**, not the write-path cost; both cores' actual usage and the denominator must be measured. Report CPU/s and read CPU/query as well when there are no input points.
2. **Isolate workload classes.** Use a disposable Linux replay, pinned image, explicit isolated topics/groups/database and fixed resources. Start with idle, reads only on a seeded copy, ingest only, and identical offered ingest plus repeatable read mix. Reads can contend for scans, decompression, aggregation and `FINAL` if used; assess read p95/p99, concurrency and rows/bytes scanned. For mixed load, the difference versus read-only is a _marginal_ estimate, not pure write CPU: concurrency, caches and merge scheduling can change. Record initial part/cache state, quota, CPU throttling, RSS, I/O latency/rate, offered and accepted rates and actual insert/part sizing by lane. Repeat/alternate arms and report spread; compare unprofiled runs to check measurement overhead.
3. **Use a controlled attribution ladder.** In the lab only replay (a) the full graph; (b) with each discovery view omitted separately, all omitted, or selectively re-enabled, holding the base table and insert path identical; (c) the same typed Kafka source into `Null` via a minimal view to estimate poll/decode/block/pipeline floor; (d) matched already typed batched foreground writes into `Null` and into an equivalent point table, then the full destination graph, to compare insert-side work. A `RawBLOB`→`Null` arm can probe per-message overhead versus typed parsing but has different schema/copy behavior and is not a replacement or a pure subtraction. Keep block shape, partition mix, order, codec, `series_id` computation and fsync comparable where relevant. Use `EXPLAIN PIPELINE` and profiled foreground replays of metric `GROUP BY` and attribute `ARRAY JOIN`/filter/aggregate transforms to explain differences. Use view-log `sum`/quantiles of duration and input/output ratios to detect fan-out; distinguish transform from destination writes using stacks and view on/off deltas. `metric_points` and `attribute_definitions` parts are separate costs even though points aren't duplicated as full payload in the catalog. Do not add all log aggregates to cgroup CPU.
4. **Separate first writes, merge debt and reads.** Within each common time window group `part_log` by table, partition and `event_type`; report `NewPart` count, median/p95 rows per new part, bytes written, `MergeParts` input/read bytes and rows, and completed merge CPU if available. Report e.g. merge input bytes per new-part byte using **matching byte bases** (physical compressed read/write counters where available), or merge input rows per verified point as a distinct work indicator. Check active parts and backlog trajectory, and include post-replay drain to a comparable state so variants cannot look cheaper by deferring merges. Use CPU stack families for parser/librdkafka, expression/array/grouping, sort/compress/write, merge, and SELECT. Leave unattributed CPU visible. `fsync` waits/throttling can make elapsed latency high even when on-CPU cost is low; do not weaken durability to make a candidate win.
5. **Check freshness and correctness alongside CPU.** Join replay manifest/producer acknowledgment time (synchronized clocks) to bounded query probes of actual point visibility and discovery visibility; measure p50/p95/p99 and worst/tail, separately for recent and late, under read load and backlog recovery. Kafka lag in records and time-to-commit are complementary, not visibility metrics; event timestamps on late data are not arrival times. Probe consistently or run a dedicated measurement pass. Do not query the live Kafka engine directly, add monitoring views, enable heavier instrumentation, alter DDL, reset offsets or stop merges in production. Read existing logs/metrics only if already collected and safe to query. — [Kafka engine integration and offset caveat](https://clickhouse.com/docs/integrations/connectors/data-ingestion/kafka/kafka-table-engine), [Mux visibility-lag measurement rationale](https://www.mux.com/blog/latency-and-throughput-tradeoffs-of-clickhouse-kafka-table-engine)

### Gaps

- Assignment reports two CPU cores serving reads/writes, about 10.3k ingest/s total, modest gain from larger batches and no gain from bypassing the row hash. These are supplied demo observations, not a pinned-build CPU breakdown. Actual block/part distributions, measured CPU use, point mix, read shape, stage samples, merge debt and freshness bounds are not supplied. No lab measurements were run. A negative hash test limits confidence in that specific optimization; it does not isolate parsing, catalog work, sorting, merges or contention.

## When would a different sink or batch format pay off?

### Takeaway

Keep the Kafka engine as the baseline. A sink benchmark is justified if typed replay and CPU stacks locate a material cost in Kafka ingestion/decode, or if there is a separately demonstrated delivery/operability requirement. Moving decoding to another process is not an end-to-end saving by itself.

### Cited Findings

- Mux (2024, first-party engineering) compared its Kafka engine with `Null`, `MergeTree` and `AggregatingMergeTree`: `ProtobufSingle` achieved 930k/500k/450k rows/s respectively; `RawBLOB`→`Null` reached 8M. Moving to 500 then 1,000 rows per Kafka message and shortening flush from 7.5 to 2.2 s together yielded ~2M rows/s sustained per server and a reported 2–6 s ingest lag range versus up to 12 s; CPU utilization went from ~25% to ~31%. This is strong evidence for investigating record-level overhead and freshness, not for a specific bug or expected uplift on 26.8.34.13: Mux's linked Altinity article mentions slow Protobuf reports, not a pinned bug/fix; `RawBLOB` bypasses typed conversion, and Mux changed both record packaging and flush timing. — [Mux engineering](https://www.mux.com/blog/latency-and-throughput-tradeoffs-of-clickhouse-kafka-table-engine), [Altinity](https://altinity.com/blog/kafka-engine-the-story-continues), [Pinned Protobuf reader](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Processors/Formats/Impl/ProtobufRowInputFormat.cpp)
- The official Kafka Connect Sink runs on Kafka Connect/Java, writes to ClickHouse via HTTP(S), supports task/topic mapping and JMX metrics, and documents schema-based RowBinary conversion versus schemaless `JSONEachRow`. Its documented Protobuf example uses Confluent `ProtobufConverter` with Schema Registry, **not** Recount's bare records. `exactlyOnce` defaults to false despite the features headline; the enabled mode uses KeeperMap and block dedup/state management, and connector internal buffering (`bufferCount`/`bufferFlushTime`, since 1.3.6) explicitly cannot be used with it. The non-exactly-once mode's `reportInsertedOffsets` is opt-in and not effective with `ignorePartitionsWhenBatching=true`. Connector JMX processing time is not labeled CPU time. — [Official connector docs](https://clickhouse.com/docs/integrations/kafka/clickhouse-kafka-connect-sink), [Recount wire contract](../../docs/telemetry-point-contract.md)
- ClickHouse recommends client-side batching where possible and its columnar `Native` format for low server parsing overhead; `Native` format and the native TCP protocol are distinct choices. HTTP supports inserts too; a native-protocol client does not eliminate server storage, view, merge or durability work. For any server-side async insert experiment, require `wait_for_async_insert=1` and independently validate acknowledgment/retry/dedup semantics on the exact configuration; do not trade reliability for speed or assume the connector's exactly-once mode works with alternative batching. — [Selecting an insert strategy](https://clickhouse.com/docs/best-practices/selecting-an-insert-strategy), [Connector buffering and tuning](https://clickhouse.com/docs/integrations/kafka/clickhouse-kafka-connect-sink)
- eBay's production Block Aggregator demonstrates **deterministic retry boundaries** using Kafka metadata and ClickHouse block deduplication; their driver was multi-table topic ingestion and duplicate prevention, not a measured CPU win for this topology. Cloudflare's 2017 first-party case describes a Go bridge going from HTTP/TSV to a native client to boost performance, but changed format/interface together on a different generation of ClickHouse and predates the Kafka engine. Both establish feasibility or design considerations, not a contemporary matched benchmark. — [eBay engineering](https://innovation.ebayinc.com/stories/block-aggregator-real-time-data-ingestion-from-kafka-to-clickhouse-with-deterministic-retries), [Cloudflare engineering](https://blog.cloudflare.com/how-cloudflare-analyzes-1m-dns-queries-per-second/)

### Inferences

- **Keep engine, test the right batching boundary.** Distinguish Kafka producer record batches (broker transport), multiple points _inside one Kafka record_ (wire format), ClickHouse blocks, and final MergeTree parts (including per-day fan-out). The demo's modest larger-batch gain does not rule out per-record cost, but confirm what changed in practice. Only if stacks/Null tests implicate per-record work, consider an isolated multirow Protobuf test with a fixed flush target, per-point identity and existing recent/late routing. This would be a deliberate wire-contract change, not a transparent setting; revalidate broker byte ceilings, partial/replayed batch behavior, nullable/unsigned/array/float fidelity, delivery lag at low volume, and downstream output. If only final part creation is costly, compare actual rows/part and read latency first; a different consumer writing identical parts leaves much of that work intact.
- **Kafka Connect vs custom native batch bridge.** Connect offers standard task deployment, metrics and configurable converters, at the price of a separate worker, conversion/serialization work, partition-dependent batching, potential schema adaptations and Keeper operations if selected. A native bridge could retain bare input, decode in its own process, bound flush by time/bytes/rows and send typed columnar blocks. It also makes Recount responsible for retry and rebalance semantics, bounded buffers/backpressure, routing and schema evolution. Either would still pay for base-table computation, fsync, catalog views and merges if they are unchanged. Benchmark ClickHouse CPU **and** end-to-end CPU (normalizer, broker delta, sink and database), memory, parts and latency; identify a deliberately valuable CPU shift if database headroom matters more than total CPU.
- **Do not conflate logical dedup with delivery guarantees.** Default engine behavior in the pinned path has a success-before-offset-commit window. After a crash, `ReplacingMergeTree` only resolves equal ordering keys during merges or with correct query-time logic; it is not a proof of exactly once, especially across dependent targets. In isolated replay test kill-after-insert/before-commit, ambiguous acknowledgment, rebalance, partial fan-out failure, restart and offset replay. Commit only after verified durability semantics; no skip-on-error path may silently advance past required points. Compare sample identities/payloads, counter continuity, case-specific catalog and read results, not just counts. — [Pinned Kafka path](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L693-L780), [ReplacingMergeTree](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/replacingmergetree), [Point contract](../../docs/telemetry-point-contract.md)

### Gaps

- No matched throughput, CPU/point, lag, or failure-behavior comparison found for these alternatives on Recount's two-core mixed workload, typed schema and full view chain. Stock connector compatibility with the unmodified bare bytes and exact optional semantics is not established. Nor is there proof that Mux's 2024 parser diagnosis transfers to this pinned build.

## Could a side stream, dictionary or CDC remove catalog work safely?

### Takeaway

Only investigate upstream catalog materialization if measured view and catalog merge CPU justify it. Keep every point and the point-table read path. A dictionary changes how reference data is looked up; it does not discover new metrics or maintain time bounds by itself.

### Cited Findings

- The catalog's definition view groups by project, metric name/kind/temporality/monotonic state/unit, carries `anyLast(description)`, and tracks min/max **event** time. Each attribute view expands its own scope and records top-level scalar key/type combinations with max event time, filtering internal continuity keys. Incremental views evaluate inserted source blocks, and a joined right-hand/dimension change does not trigger recomputation. — [Recount DDL](../../infra/clickhouse/schema.sql.in#L64-L139), [ClickHouse incremental views](https://clickhouse.com/docs/materialized-view/incremental-materialized-view)
- ClickHouse dictionaries are lookup structures for reference data, with query-time or insert-time use and layout-dependent memory/refresh behavior. A `LIFETIME` schedules refresh or cache invalidation, not guaranteed per-write visibility; failed reloads can leave old data served. Cloudflare's engineer reported substantial memory and source-dependency costs in deployed dictionaries and used file bundles to decouple production/consumption. This supports an enrichment/operator trade-off, not catalog CPU savings or acceptable refresh lag here. — [Dictionaries](https://clickhouse.com/docs/dictionary), [Dictionary lifetime](https://clickhouse.com/docs/reference/statements/create/dictionary/lifetime), [Cloudflare meetup account](https://clickhouse.com/blog/how-cloudflare-processes-hundreds-of-millions-of-rows-per-second-with-clickhouse)
- Relational CDC captures changes to an existing source of truth (e.g., ClickPipes Postgres uses logical replication with snapshot/sync settings, on ClickHouse Cloud). Salla's Timeplus vendor write-up with customer quotes reports lower ClickHouse resource use after moving MySQL CDC transformation/enrichment and batching out of ClickHouse across thousands of tables. Several variables changed and extra compute was deployed. This is a directional case, not evidence for an append-only points workload or a net CPU/point reduction. — [ClickHouse Postgres CDC](https://clickhouse.com/docs/integrations/clickpipes/postgres), [Timeplus/Salla case](https://www.timeplus.com/post/customer-story-salla)

### Inferences

- **Side stream of catalog state:** An isolated candidate can derive catalog contributions from the same durable normalized records and coalesce batches by project-qualified key, with a maximum visibility delay. Frequency savings depend on repeated keys and small change volume; CPU to walk point/resource attributes may merely move to the normalizer or a second Kafka consumer. Sending only “first time seen” is incorrect: late data can move first-seen backwards, newer data moves last-seen forwards, and descriptions may change. Establish what `anyLast` means to product queries under unordered merges/replays before choosing a version/tie-break; don't silently reinterpret it as latest event time. Keep scope/type separation, filtering, `NULL` vs sentinel behavior and tenant boundaries. Test catalog catch-up after consumer restart, rebalance, duplicate replay and skew between fact/cat visibility; independent acknowledgments require an explicit reconciliation strategy. Do not propose a second permanent data path before incremental view/merge deltas show that it buys meaningful headroom.
- **Dictionary:** Consider only when a small existing dimension is repeatedly joined, or fully materialized point-independent reference state can be served as keyed lookups. It is not a replacement for append-only point storage or an enumerated discovery feed without a separate catalog producer and read path. Query-time lookup may shift cost onto the same two cores and returns a current/refreshed snapshot unless versions are explicit; insert-time lookup freezes the value available at ingestion and will not correct historical points automatically. Measure hit/miss/refresh latency and memory under load; missing/stale keys cannot hide valid points or change historical semantics.
- **CDC:** Appropriate to replicate authoritative metadata _if it exists_ upstream. CDC of definitions cannot infer keys or event-time extrema from telemetry unless another job computes and transactionally publishes those facts; adding a transactional hop for every point adds work. Prefer diagnosis in the current design over installing a CDC platform to solve a hypothetical hotspot.
- **Decision gate:** Predeclare acceptable CPU headroom or capacity improvement, and use the simplest isolated change that explains a reproducible gain above run variance. Keep the full expected point payload and logical identities, read results/dedup and counter semantics, catalog results, durability and retry behavior. Require non-regression in visibility and read tails at sustained load, bursts and recovery, with merge debt back at a comparable level. If CPU is dominated by reads or base writes/merges, transport replacement or catalog extraction targets the wrong work. If the demo remains within its freshness/correctness/performance budget and no structural benefit is measured, retain the current design.

### Gaps

- No catalog CPU, key-repetition or change-rate measurement, reference-data source, required visibility SLO, or deterministic description rule was supplied. No controlled study found for moving an equivalent Recount discovery catalog upstream. Both the net savings and the feasibility of preserving catalog visibility under independent delivery are unproven.
