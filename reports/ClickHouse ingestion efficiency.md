# Pack Kafka records, keep every point

**Test bounded multi-point Protobuf records first on the two-core-capped Oracle ARM setup, with the real Rust normalizer and dashboards running.** In the strongest local replay, packing up to 128 points into each Kafka record raised mid-replay throughput from **46.2k to 69.2k points/s (+50%)** and lowered ClickHouse CPU from **26.29 to 14.35 CPU seconds per million points (−45%)**. The 16,384-row insert target, both point-table fsync settings and all discovery views stayed in place; full ordered RowBinary SHA-256 and both grouped catalogs matched. That result came from preloaded, single-day synthetic data, not the deployed normalizer, representative telemetry, live dashboard traffic or multi-day late arrivals. Start with recent traffic only and keep the existing late-lane framing and partition guard. In parallel, compare 16,384 versus 32,768 rows with the unchanged wire format as the lower-risk fallback, and treat a shorter flush as a separate freshness experiment rather than assuming faster backlog replay makes sparse dashboards fresher ([wire receipt](../.state/semaphore-oracle/clickhouse-benchmark-wire.json), [compute receipt](../.state/semaphore-oracle/clickhouse-benchmark-compute.json), [point contract](../docs/telemetry-point-contract.md)).

## Packing Kafka records beat enlarging ClickHouse inserts locally

Recount already batches at several levels: librdkafka can send many Kafka records in one broker request; each normalized record currently contains one bare `AnalyticalPoint`; the native Kafka source combines decoded rows into a ClickHouse block; and a block can create parts in each event-day partition it touches, plus parts in the catalog targets. **Packing changes the second boundary, not the number of points or their representation in ClickHouse.** The packed arm writes a sequence of varint length + `AnalyticalPoint` bytes per Kafka record, with the same descriptor and ClickHouse `Protobuf` rather than `ProtobufSingle`. Mux reported higher sustained throughput and lower lag after switching to multiple rows per Kafka record **and** shortening its flush interval; its scale and combined intervention make it a useful precedent, not a capacity forecast or a diagnosis of Recount's pinned parser ([point contract](../docs/telemetry-point-contract.md#binary-mapping-and-schema-deployment), [ClickHouse Protobuf](https://clickhouse.com/docs/interfaces/formats/Protobuf), [Mux engineering](https://www.mux.com/blog/latency-and-throughput-tradeoffs-of-clickhouse-kafka-table-engine)).

The local A/B/B/A replay used **900,000 points per arm**, distributed 10%/20%/70% across three partitions, with one ClickHouse consumer. Packing cut the message count from **900,000 to 7,033**. The poll cap necessarily changed units in practice: 1,024 single-point records versus 16 packed records, up to 2,048 decoded rows per poll. Thus the result measures a bounded configuration change, not the isolated cost of the parser; fixed row _targets_ do not guarantee identical realized blocks. All four runs verified 900,000 distinct sample IDs, the same ordered full-row binary digest, and both complete grouped catalogs on this fixture. Rows/s is the **10%–90% replay slope**; CPU is ClickHouse container usage through catch-up, not a matched-rate or post-merge-drain measurement. The Python producer preseeded both arms with LZ4 and a 20 ms linger; the Rust normalizer uses Zstd. Neither local producer measurements nor this replay establish whole-stack savings, crash safety or a dashboard freshness improvement ([wire harness](../.state/semaphore-oracle/bench-clickhouse-wire.py), [wire receipt](../.state/semaphore-oracle/clickhouse-benchmark-wire.json), [normalizer runtime](../apps/normalizer/src/runtime.rs#L121)).

The earlier receipts give smaller or negative alternatives. At 32,768 versus 16,384 rows, mid-replay throughput improved **about 6%** in the compute run; the series-hash bypass did not help. Omitting all discovery increased throughput **about 23%** and lowered ClickHouse CPU per point **about 4–5%**. That is a diagnostic contrast, not an acceptable configuration or evidence that views account for 23% of CPU. Sorting and deduplicating each row's discovery array before `ARRAY JOIN` preserved the fixture's catalog but reduced the mid-replay slope **about 7%** and increased CPU per point **about 2%**; completion times were close. Compare only within each receipt: their baselines vary, and the gains cannot be added ([compute receipt](../.state/semaphore-oracle/clickhouse-benchmark-compute.json), [dedup receipt](../.state/semaphore-oracle/clickhouse-benchmark-dedup.json)).

## Pack in the normalizer without delaying sparse traffic

Prototype packing **within a single accepted raw request**, bucketing by the existing destination topic and explicit stream-derived partition. Start with smaller row caps such as 32 or 64 alongside 128, plus an **encoded-byte cap including every length prefix**. Send partial buckets at request completion rather than waiting for other requests to fill them; do not impose an artificial batching delay on sparse input. Split before the next row would exceed a cap, and allow every currently valid wide point to fit by itself in the new framing. Keep bounded workers, buffers and backpressure. Keep validation, original observation positions, sample and stream IDs, and the current clock-based recent/late routing. Preserve idempotent producer configuration and `acks=all`: acknowledge a raw record only after **all** of its output records are confirmed and advance only the contiguous completed raw offset prefix. One Kafka record's offset can now cover many points; a partial publish or ambiguous acknowledgment must replay the same logical points, not mint new identities. Revalidate producer/topic/broker/replication and consumer fetch/receive budgets, decoded-memory headroom and effective per-partition retention. Use isolated topics with the correct reader for each framing; never point the new parser at retained bare records or mix both framings on one topic ([normalizer runtime](../apps/normalizer/src/runtime.rs#L40), [routing and acknowledgments](../docs/telemetry-point-contract.md#routing-batching-and-acknowledgement), [transport limits](../infra/README.md#L140), [librdkafka settings](https://github.com/confluentinc/librdkafka/blob/v2.12.1/CONFIGURATION.md)).

**Keep late traffic single-point at first.** In the pinned 26.8.34.13 source, ClickHouse finishes a poll before checking the decoded row target. With a block target `B`, effective poll cap `P` records and at most `M` decoded points per record, the source can accumulate **`B − 1 + P × M`** rows before emitting a block. For default late `B = 64`, `P = 32`, `M = 1`, the worst case is 95 distinct days, under the default partition ceiling of 128. With `M = 128`, even one full message can add 128 rows to an already partially filled block. Same-day grouping _within_ a record is not by itself a proof about the block. Keep the throwing guard; do not pack late until conservative row or distinct-day bounds are proved for the entire insert and exercised with arbitrary-day replays. Also exercise recent backlog spanning multiple routing days: few event days at publication does not imply few across retained offsets ([pinned poll cap](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L588-L605), [pinned source loop](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/KafkaSource.cpp#L289-L327), [Recount partition guard](../infra/README.md#L148)).

Keep Zstd fixed for the first real-normalizer A/B. If profiles implicate compression, test Kafka producer/topic Zstd versus LZ4 separately and measure CPU across the normalizer, broker and ClickHouse plus retained bytes on the hottest partition. On the unchanged wire format, use measured producer queue waits, delivery batches and preparation-lane utilization before tuning linger, queue size or preparation concurrency; extra linger costs sparse freshness, and more workers compete for shared ARM CPU and memory. Keep the Kafka engine unless profiling justifies a replacement: an alternate client writing batched columnar `Native` can reduce database parsing, but it must own durable writes, replay boundaries, rebalances and backpressure. Kafka Connect adds a worker, its documented Protobuf converter uses Schema Registry rather than these bare bytes, and its exactly-once mode has separate Keeper state and buffering constraints. Neither alternative removes sorting, fsync, catalog writes or merges ([normalizer and byte budgets](../infra/README.md#L140), [ClickHouse insert strategies](https://clickhouse.com/docs/best-practices/selecting-an-insert-strategy), [Kafka Connect sink](https://clickhouse.com/docs/integrations/kafka/clickhouse-kafka-connect-sink)).

## Tune ClickHouse for the bottleneck the dashboards actually share

Capture effective DDL, image digest and configuration first: the checked-in recent renderer is **4,096 decoded rows / 1,024 records per poll**, not the 16,384-row replay baseline. Keep **one recent consumer** and a **2 s flush target** while testing 16k versus 32k at fixed poll cap on the current wire. More consumers distribute assignments across partitions, not work within the hot partition; earlier local multi-consumer tests regressed, and extra flushes can create smaller parts. Larger targets help when actual blocks and parts get larger. Under sparse traffic the timer often wins, and the timer is not an end-to-end visibility bound. Once the best capacity arm is known, compare a shorter recent flush, for example **2 s versus 1 s**, at fixed framing and row target; reject a freshness win that creates unbounded part debt or worse dashboard query tails. Only tune poll and prefetch with evidence: compare a modest poll-cap increase if polls routinely fill; if polls are small or empty despite backlog, inspect fetch sizes, queue occupancy and backoff before increasing the queue's message target inside the byte budget. Broker fetch wait, local poll timeout and consumer group liveness are separate controls. Investigate schedule slots only if active recent, late and participant tasks are demonstrably waiting with CPU headroom ([renderer](../crates/telemetry-schema/src/ddl.rs), [local consumer comparison](../.state/semaphore-oracle/clickhouse-benchmark-shared-worker.json), [Kafka engine](https://clickhouse.com/docs/engines/table-engines/integrations/kafka), [librdkafka settings](https://github.com/confluentinc/librdkafka/blob/v2.12.1/CONFIGURATION.md)).

Keep `ReplacingMergeTree`, event-day partitions, the full `ORDER BY`, both fsync flags and duplicate-sensitive `FINAL` reads. **Change physical layout only when profiles support it.** If marks dominate, compare granularity 256 with 512/1,024 on fresh disposable tables and test narrow project/time/series queries for read amplification and p95/p99. If compression dominates, try lossless targeted codecs rather than a global setting: LZ4 for hot columns not already using it, or Zstd(1) when disk work dominates; test delta encoding only where actual in-part order gives timestamp locality. If writes or merges dominate, inspect Compact/Wide part mix, actual fsync/part sizes, merge amplification and quota contention before varying thresholds or merge block sizes. Use sort counters before considering pre-sorted input; independent producer batches cannot guarantee ordering after Kafka partitions are combined. Do not disable merges or weaken fsync, use asynchronous fire-and-forget, enable parse skips or ignore MV errors. The pinned Kafka engine inserts synchronously before committing offsets; replay is possible because storage and offset commits are not transactional ([point DDL](../infra/clickhouse/schema.sql.in#L3), [ReplacingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree), [parts](https://clickhouse.com/docs/parts), [compression](https://clickhouse.com/docs/data-compression/compression-in-clickhouse), [pinned insert and commit path](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L708-L776)).

## Make discovery cheaper without narrowing the catalog

The three incremental views run on inserted blocks and write real parts. **Keep them synchronous initially; profile each view separately in disposable runs.** If attributes dominate, test projecting only path and kind, filtering out containers, nested paths and reserved markers before `ARRAY JOIN`, and delaying slash removal until after grouping where the plan permits. There is less to gain if almost every node qualifies. A second candidate tags the filtered point and resource arrays with scope, concatenates them and expands once to avoid a second query/target insert; independent expansions can multiply rows, and zipping arrays pairs positions rather than scopes. On workloads with many repeated resource shapes, optionally group by project/metric and the full ordered array of eligible `(path, kind)` pairs with a partial `max`, then expand and group again. That is exact for `max`; grouping by a hash alone is not. No per-row sort/distinct is warranted by the local result ([catalog DDL](../infra/clickhouse/schema.sql.in#L64), [incremental views](https://clickhouse.com/docs/materialized-view/incremental-materialized-view), [ARRAY JOIN](https://clickhouse.com/docs/sql-reference/statements/select/array-join), [array functions](https://clickhouse.com/docs/sql-reference/functions/array-functions)).

Use full grouped bidirectional comparisons at **nanosecond precision**, not capped web responses. Preserve attribute keys `(project_id, metric_name, scope, attribute_key, value_kind)`, kinds 2–6, top-level scalar paths, literal `~0` and `~1` escapes, scope-specific marker exclusions and exact `max` event time. Do not add instrumentation-scope attributes. Preserve metric keys `(project_id, metric_name, metric_kind, temporality, monotonic_state, unit)`, unknown monotonicity `2` and exact event-time minima/maxima. Retain reader-side grouping across parts. An old arrival can introduce a new key or move a variant's first-seen backwards; a later event moves its last-seen forwards. `anyLast(description)` is already nondeterministic, not latest-by-event-time: compare descriptions exactly on fixed-description fixtures and make any deterministic description rule a separate product decision ([catalog DDL](../infra/clickhouse/schema.sql.in#L64), [web discovery reads](../apps/web/src/analytics/discovery.server.ts), [AggregatingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/aggregatingmergetree), [`anyLast`](https://clickhouse.com/docs/sql-reference/aggregate-functions/reference/anylast)).

If discovery proves expensive **and** its freshness budget permits a delay, try an arrival-based microbatch fed by a durable stage or an independent consumer with checkpoints per topic/partition for both lanes. Derive exact, project-qualified contributions from the same normalized data, coalesce partial `min`/`max` states, and checkpoint only after all required outputs succeed. Reconcile partial fan-out and replay; tie staging to successful point insertion if a catalog entry must not be visible before its point. A fixed event-time lookback misses arbitrarily late discoveries; dirty-day rescans are a reconciliation option but can be expensive and cannot recover replaced or expired rows. Full refresh is reasonable only against a small, complete source: the point table can lose observations needed for an “ever sent” catalog through replacement, and ordinary refresh `APPEND` does not make scans incremental. `APPEND INCREMENTAL` is newer than the 26.8 pin and requires a plain `MergeTree` source, not this `ReplacingMergeTree`. Dictionaries can accelerate lookups of already-authoritative metadata, and CDC can replicate it; neither discovers keys or calculates event-time bounds without an additional producer ([refreshable views](https://clickhouse.com/docs/materialized-view/refreshable-materialized-view), [26.9 incremental refresh](https://clickhouse.com/blog/clickhouse-release-26-09#incremental-refreshable-materialized-views), [dictionaries](https://clickhouse.com/docs/dictionary), [Postgres CDC](https://clickhouse.com/docs/integrations/clickpipes/postgres)).

## Qualify changes under dashboard load and replay

On the **two-core ClickHouse cap on shared Oracle ARM**, use isolated databases, topics and groups. Record the current single-point baseline, then alternate it with the real-normalizer packed recent arm at the same 16,384-row/2 s settings and a deliberately bounded decoded poll. Hold readers, quota, memory, fsync, views and initial data/part state constant. Use a representative manifest with narrow and wide points, real attribute cardinalities and partition skew, sparse traffic, bursts, retained recent backlog across days and concurrent arbitrary-day late traffic. Compare matched offered rates first, then step up to the highest sustained durable rate at which **both hottest-partition lag and merge debt stabilize**. Measure finite-backlog catch-up with live arrivals continuing and let merges drain to a comparable state. Run the 32k unchanged-wire and shorter-flush tests separately so transport, block and timer effects stay interpretable ([Kafka consumer metrics](https://clickhouse.com/docs/operations/system-tables/kafka_consumers), [part log](https://clickhouse.com/docs/operations/system-tables/part_log), [replay and retention](../docs/kafka-recovery.md)).

Set freshness and reader-tail budgets before running. Measure **acknowledged arrival to actual query visibility** for points and catalog separately, and dashboard query p50/p95/p99 under load; record normalizer delivery and broker commit lag as intermediate signals, not visibility. Divide ClickHouse cgroup CPU by verified logical points and record total stack CPU per point, throttling, RSS, flush/part histograms, disk and merge work, and broker-committed offsets/retention per partition. If the result is unclear, compare reads-only, ingest-only and mixed windows. Attribute with per-view events when present, part logs and on-CPU sampling; query/view elapsed times are not additive CPU budgets, and internal Kafka work need not appear in client-side processor logs. A typed Kafka→`Null` replay and an equivalent foreground typed insert can bound portions of the work without claiming that either is a deployable equivalent ([Linux cgroup CPU accounting](https://docs.kernel.org/admin-guide/cgroup-v2.html#cpu), [view log](https://clickhouse.com/docs/operations/system-tables/query_views_log), [processor profile log](https://clickhouse.com/docs/operations/system-tables/processors_profile_log), [sampling profiler](https://clickhouse.com/docs/concepts/features/performance/troubleshoot/sampling-query-profiler)).

**Make correctness and recovery pass/fail gates.** Compare a manifest of expected logical samples against full-key ordered RowBinary under `FINAL`, and compare complete grouped catalogs in both directions. Include absent versus zero/false/empty values, exact integer and float-bit fixtures, nested versus escaped slash keys, reserved markers, repeated and rare attributes, late-discovered variants, and out-of-order first/last times. Test crashes before storage completion and after durable writes but before Kafka commit, partial normalizer publication, ambiguous acknowledgments, rebalance and restart on the same isolated group. Reject missing points, silently skipped errors, changed logical results or counter continuity, and catalog drift. Exact retries may produce physical duplicates; conflicting content under an immutable sample ID is already outside the contract and is not a first-writer-wins guarantee. Choose a candidate only if its gains exceed repeat-run variation without breaking the declared point/catalog visibility, read tail, retention or recovery budgets ([point identity and replay](../docs/telemetry-point-contract.md#sample-identity-and-retry-rules), [pinned commit sequence](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/StorageKafka.cpp#L742-L776)).

## Conclusion

Transport efficiency and dashboard freshness are separate controls. If packing creates verified CPU headroom but sparse visibility stays unchanged, spend that headroom on a faster recent flush only if the resulting parts and read tails remain sustainable. If packing merely shifts CPU upstream or worsens recovery, the unchanged-wire batch and profiling experiments still leave a path to improvement without changing the delivery contract.
