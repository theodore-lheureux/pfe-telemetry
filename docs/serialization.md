# Serialization

The [telemetry point contract](telemetry-point-contract.md) defines generated raw messages and one bare analytical Protobuf point per Kafka record. The ingestion API publishes raw records; the RustStream normalizer publishes points; ClickHouse's native Kafka engine and non-aggregating materialized view ingest typed rows. Shared types and columns derive from one schema. Normalized Kafka has one current encoding, not a parallel JSON or legacy path.

The pipeline uses OTLP/gRPC with binary Protobuf for telemetry transport and Protobuf for retained ingestion records. ClickHouse stores historical telemetry; TanStack Start serializes application RPCs. Rust values can pass between collection and processing modules without serialization when they share a process.

The selection favors generated types, application instrumentation in several languages, preservation of measurement context and recoverable processing. Configurable safety defaults exist; payload size, CPU cost and decoded memory still need representative measurement before sizing a workload or changing compression/batching settings.

## Formats by layer

| Layer                                               | Representation                                                | Reason                                                                                                                                             |
| --------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sensor or operating system to Rust collector        | Native Rust values                                            | Preserve numeric types and measurement context without a wire format inside the process.                                                           |
| Application code to instrumentation library         | Native language API                                           | Developers record counters, gauges, histograms, and timed operations through an existing OpenTelemetry library or an optional convenience wrapper. |
| Instrumented application to ingestion               | OTLP/gRPC, binary Protobuf                                    | Accept standard gRPC exporters across languages and keep application instrumentation independent of the collector implementation.                  |
| Collector disk buffer                               | SQLite rows containing OTLP Protobuf bytes and retry metadata | Keep the encoded batch and its identity stable through retries and collector restarts.                                                             |
| Collector to Rust ingestion API                     | OTLP/gRPC, binary Protobuf                                    | Use the same telemetry definitions for external measurements and application signals.                                                              |
| Ingestion API to raw Kafka                          | Generated `RawRecord` Protobuf                                | Retain the supported decoded request, immutable identity and trusted resource/security context before analytical processing.                       |
| Normalizer to normalized Kafka to native ClickHouse | One bare `AnalyticalPoint` Protobuf message per Kafka record  | Bound each point and total output; consume using `ProtobufSingle` and the matching schema artifact.                                                |
| TanStack Start server functions to browser          | Start's native RPC serialization                              | Preserve internal `Date` values and return authorized UI-shaped data with exact telemetry integers represented explicitly.                         |
| HTTP/JSON or text integrations                      | Explicit JSON/text conversion                                 | Use ISO dates and decimal 64-bit values at actual text boundaries, not as an internal RPC requirement.                                             |
| Export to another telemetry backend                 | OTLP for supported signals, if implemented                    | Reuse the standard model where the destination accepts the same signal and transport; portable exports are not implemented.                        |

SQLite transactions distinguish committed pending batches from interrupted writes. The Protobuf message definition describes the payload, while SQLite stores its delivery state. ClickHouse history is separate from the collector's pending-upload buffer and broker retention. Portable exports are not implemented.

Execution registration and other application requests belong to the TanStack Start application API. They are separate from OTLP metric export; trace storage remains unimplemented. Current execution windows select source/optional host context rather than defining a complete distributed-participant model.

## Alternatives considered

| Format      | Advantages                                                                                                                                                | Costs and limits                                                                                                                                                                                                                                                       | Use                                                                                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| JSON        | Readable, widely supported, and convenient for HTTP APIs and diagnostics.                                                                                 | Verbose field names before compression. Explicit validation and numeric-representation rules are still needed. JavaScript cannot represent every 64-bit integer exactly as a number. [Numeric interoperability](https://www.rfc-editor.org/rfc/rfc8259)                | Web and control APIs; an alternative telemetry encoding for interoperability checks. |
| Protobuf    | Explicit field types, generated code, binary encoding, and defined evolution rules. [Language guide](https://protobuf.dev/programming-guides/proto3/)     | Requires schema and code-generation tooling. Generated types do not validate units, identities, or measurement meaning. Binary captures need decoding tools for inspection.                                                                                            | Telemetry and retained ingestion records.                                            |
| Avro        | Typed records, writer/reader schema resolution, and established streaming integrations.                                                                   | Decoding needs access to the writer schema. Adopting it would add another schema model and conversion from OTLP. A registry is useful in some deployments but is not required by Avro itself. [Avro specification](https://avro.apache.org/docs/1.12.0/specification/) | Reconsider if an Avro-based downstream integration becomes necessary.                |
| MessagePack | Binary representation of common JSON-like values, including integer types. [Format specification](https://github.com/msgpack/msgpack/blob/master/spec.md) | The format alone does not supply the shared schema, generated domain types, or evolution policy needed by the collectors. A separate contract would still be required.                                                                                                 | No initial use.                                                                      |
| Arrow IPC   | Typed column batches for bulk transfer and analytical processing. [Arrow format](https://arrow.apache.org/docs/format/Columnar.html)                      | Adds columnar conversion and browser or client integration work. Kafka does not impose Avro. Protobuf can be used with Kafka or another broker. A schema registry would be an additional deployment choice; registries such as Confluent's support Protobuf and JSON Schema as well as Avro. [Supported registry formats](https://docs.confluent.io/platform/current/schema-registry/fundamentals/serdes-develop/index.html)

## OTLP and transport

Protobuf defines message encoding. OTLP adds shared telemetry definitions and export behavior. HTTP and gRPC are transport choices. Reusing an OpenTelemetry `.proto` file alone does not make an endpoint OTLP-compatible.

OTLP/gRPC is the selected ingestion transport. Tonic exposes the generated service interfaces and handles gRPC framing, compression, and status codes. OTLP/HTTP with binary Protobuf remains an alternative if an integration requires HTTP. OTLP/HTTP also defines JSON encoding using the same schemas; it is an interoperability option, not a separate application metric model. HTTP transports are not implemented. [OTLP specification](https://opentelemetry.io/docs/specs/otlp/), [ingestion API](ingestion-server.md)

The generated `MetricsService.Export` method receives its standard request. Requests with validated observations return the standard empty success response only after confirmed raw Kafka publication. Authenticated zero-point requests return that response after authority and validation checks without publication; empty-export success is not a publication or downstream-health probe. Execution metadata or a custom receipt does not replace OTLP bodies. The API requires an authoritative credential database, supports uncompressed/gzip metrics, and returns `UNIMPLEMENTED` for traces. Startup configuration, health and admission limits are in the [ingestion API reference](../apps/ingestion-api/README.md).

Admission validates the whole request, including exact normalized-size preflight, before any raw publication. There is no partial OTLP success. That request-wide acceptance boundary does not create an atomic analytical-visibility boundary: output rows can become queryable at different times. Exporters must not retry a response that reports partial success from another OTLP receiver.

## Generated types and extensibility

The collector and ingestion API use existing generated Prost/Tonic types from `opentelemetry-proto`. The shared schema crate generates project-owned raw/normalized messages, a descriptor and analytical SQL columns from [`recount.proto`](../crates/telemetry-schema/proto/recount.proto). Its explicit projection converts supported OTLP observations into analytical fields; it is not a second collector metric model. [OpenTelemetry generated types](https://docs.rs/opentelemetry-proto/latest/opentelemetry_proto/), [Prost](https://github.com/tokio-rs/prost)

Typed telemetry does not require a generated field for every application metric. A metric has an explicit structure for its name, unit, value type, temporality, timestamps, and attributes. An application can introduce a name such as `solver.iterations` without rebuilding the collector. Application-specific generated wrappers can remain in the application's code.

Resource identity is project-qualified and distinct from reporting source and execution context. Standard resources need no invented Linux PID/boot fields. Adapter-local identities and exact independent-resource bindings are resolved from enrolled authority, never payload topology. Supported relationship/provenance fields preserve evidence without implementing inventory or execution attribution. Adding a standard authorized metric name does not require a new wire schema or admission to the collector-only catalogue.

Optional convenience libraries would configure existing OpenTelemetry SDKs, attach execution context, and provide simple metric and operation methods. They would reuse aggregation, batching, export, and transient retry behavior. Each supported language still needs initialization and lifecycle integration; generating messages does not generate that API. [Metrics SDK](https://opentelemetry.io/docs/specs/otel/metrics/sdk/), [Tracing SDK](https://opentelemetry.io/docs/specs/otel/trace/sdk/), [OTLP exporter](https://opentelemetry.io/docs/specs/otel/protocol/exporter/)

Applications already using OpenTelemetry can send directly without a project-specific library. Convenience libraries should reuse an application's existing telemetry configuration and context where possible. Automatic machine and process collection remains independent of application instrumentation.

## Measurement fidelity and custom records

Preserve collection time, measurement window, units, scope, source, and quality information. Record whether a value is a gauge, cumulative counter, interval delta, or estimate. A missing or inaccessible measurement must not become a measured zero. An exported histogram summarizes observations; it does not preserve every original observation. Collection frequency, aggregation, and trace sampling determine what evidence remains available. [Metrics data model](https://opentelemetry.io/docs/specs/otel/metrics/data-model/)

Ordinary scalar OTLP metric values use signed 64-bit integers or doubles. A full-range unsigned hardware counter therefore needs a deliberate representation if exact preservation is required. This limitation concerns scalar values, not every integer field in OTLP. [Metric definitions](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/metrics/v1/metrics.proto)

A grouped Linux hardware-counter read is a candidate for a specialized record. It can contain raw counter values, event definitions, a group identity, and enabled/running durations. Keeping these together allows later analysis to inspect multiplexing coverage and distinguish measured counts from scaled estimates. Interval estimates require deltas over the same window, and zero running time means unavailable data. [Linux performance counters](https://man7.org/linux/man-pages/man2/perf_event_open.2.html)

OTLP attributes or a structured log body can carry custom context, but other tools will not automatically understand its semantics. A custom Protobuf record becomes useful when explicit fields and exact source representation are needed. [Structured log bodies](https://opentelemetry.io/docs/specs/otel/logs/data-model/)

A future custom-record design would need an explicit RPC/payload-kind contract, generated types, validation and storage mapping. Any OTLP projection would identify conversions or omissions. That is a research option, not an implemented payload kind, alternative normalized format or compatibility reader. No specialized record is required for the current CPU, memory and I/O measurements.

Trace and execution identities remain distinct. One execution can contain several traces. Cross-process relationships require propagated trace context or explicit span links; external process measurements alone cannot reconstruct them. Trace storage must preserve parent identities and links, and tolerate spans arriving out of order. [Context propagation](https://opentelemetry.io/docs/concepts/context-propagation/), [Spans and links](https://opentelemetry.io/docs/concepts/signals/traces/)

Standard trace export normally sends completed spans. A live view of an operation that has not finished needs separate lifecycle information; external resource measurements remain available while that operation runs. [Span export](https://opentelemetry.io/docs/specs/otel/trace/sdk/)

## Retention and replay

The Linux collector stores metrics payload bytes, UUIDv7 batch IDs, creation timestamps, epochs and point counts in SQLite. It sends the shared batch metadata with profile `linux`, preserving body order and identity across retries. Standard OTLP without that optional batch extension is supported under profile `standard`. Authentication and root/resource grants determine permitted scope; values in a payload do not establish authority. See [collector configuration](../apps/collector/README.md) and [sample identity](telemetry-point-contract.md#sample-identity-and-retry-rules).

The generated raw record contains trusted project/source, server record identity, receipt time, payload kind, optional client batch identity, resolved resource-access contexts and the supported re-encoded OTLP request. Retained replay validates that stored shape without checking current credential age/revocation or changing original positions. There is no separate prototype-version discriminator or format negotiation.

Prost discards fields unknown to its generated schema during decoding. Metric names and attributes are known OTLP fields and remain available; future protocol fields may not survive re-encoding. Exact original-payload retention would require capture in a custom Tonic codec and an adapter to the typed handlers. That additional implementation is separate from ordinary replay. [Prost decoding](https://docs.rs/prost/latest/prost/), [Tonic codecs](https://docs.rs/tonic/latest/tonic/codec/trait.Codec.html)

Recount collectors reuse batch identities on retry. Third-party exporters do not necessarily provide equivalent identities. Server-assigned record IDs make replay of an accepted record stable, but cannot identify an independent later submission as the same observation. Original positions remain part of sample identity regardless of worker regrouping. Changed content under a reused client identity is a protocol violation, with no permanent first-writer ledger or promise of complete conflict detection.

Protobuf serialization is not canonical. Do not derive a logical batch identity from serialized-byte equality or a payload hash. The shared typed identity rules, original positions and artifact checksums serve different purposes. [Serialization limits](https://protobuf.dev/programming-guides/serialization-not-canonical/)

Project-owned schemas define the current fields and types. Distinguish absent scalar values from present zero, pin code-generation dependencies and reject invalid retained records without advancing their offsets. Ship the same `recount.proto` and generated columns to native consumers; schema cache refresh and explicitly scoped disposable-state recreation belong to [stack operations](../infra/README.md), not implicit conversion or startup reset.

ClickHouse stores native scalar, distribution and attribute projections, with bounded supported evidence in byte columns. A Kafka body is exactly one bare message, consumed as `ProtobufSingle`; there is no custom batch envelope, registry prefix or JSON fallback. Multirow file/HTTP fixtures and query exports separately use the standard length-delimited `Protobuf` stream format, not a second Kafka reader. The [binary mapping](telemetry-point-contract.md#binary-mapping-and-schema-deployment) defines fields and deployment requirements.

Current readers query logical unique samples (`FINAL`) before bucketing and preserve exact nanosecond/integer values as decimal strings in their DTOs. Internal application RPCs retain native `Date` values through Start serialization; ISO conversion belongs only at text/JSON integration boundaries. Ordinary chart doubles can remain numbers when their declared range/precision permits it. Arrow IPC would need a measured bulk-transfer requirement.

## Validation

| Check                                                                               | Expected result                                                                                                                |
| ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Send standard metrics from exporters in two languages and exercise trace rejection. | Supported metrics require no project-specific SDK; traces remain explicitly unimplemented.                                     |
| Compare representative batched JSON and Protobuf, with and without compression.     | Record payload size, encode/decode CPU cost, allocations, collector overhead, and ingestion delay.                             |
| Encode, retain, decode and natively store known measurements.                       | Values, units, times, context, optionality and declared precision survive each implemented boundary.                           |
| Receive an unsupported profile or invalid current record.                           | Reject the request or halt the affected input without silently selecting another format.                                       |
| Retry an identified collector batch and replay its broker record.                   | Identities remain stable and duplicate-sensitive queries are unchanged before/after physical replacement.                      |
| Retry third-party exports without stable batch identities.                          | Behavior matches the documented deduplication limits.                                                                          |
| Truncate a disk-buffer write or restart during publication.                         | Recovery finds complete records and reports incomplete data without inventing samples.                                         |
| Export large integers and timestamps to the browser.                                | JSON conversion preserves the declared precision.                                                                              |
| Inject malformed batches, oversized requests, and invalid context.                  | Rejection follows the declared protocol and access rules.                                                                      |
| Evaluate future cross-process tracing separately.                                   | Propagation, storage and execution associations need their own implementation and evidence; metric fixtures do not prove them. |

Batch size, export interval, compression threshold, and buffer capacity should follow these measurements. Persistent collector buffering protects locally committed pending batches until backend acceptance; application-side memory buffers and export queues have their own failure and capacity limits.

Shared fixture round trips, normalizer Kafka tests and full native-ingestion faults are distinct checks. Use host compilation and Docker-only application/test execution with explicitly allocated resources. Provisional body/output/concurrency limits are not a peak-memory or production-capacity proof.
