# Telemetry point contract

Recount metrics use authenticated OTLP input, raw Kafka retention, a Rust normalizer, normalized Kafka records and native ClickHouse point ingestion. PostgreSQL supplies credential and application authority only. Partial and eventual chart visibility are accepted; Kafka acknowledgement does not promise queryability.

The collector, ingestion API, normalizer, native ClickHouse consumer and authorized readers use this contract. PostgreSQL stores current credential/root/resource grants and application metadata, not telemetry acceptance or completeness manifests. No discarded prototype format is supported alongside it.

The ingestion API performs exact normalized-output preflight before raw Kafka publication. The normalizer revalidates retained input before publishing analytical rows. The 1 MiB normalized row/record and 16 MiB total-output defaults are provisional configurable safety values, not production capacity guarantees.

## Authoritative types and boundaries

[`recount.proto`](../crates/telemetry-schema/proto/recount.proto) generates `RawRecord`, the internal `NormalizedPoint`, the normalized wire projection `AnalyticalPoint`, security/resource references and original positions. [`recount-telemetry-schema`](../crates/telemetry-schema) owns those types, canonical hashing, bounded normalization and the explicit analytical projection. [`recount-telemetry-validation`](../crates/telemetry-validation) owns pure semantic checks, metadata parsing, the collector catalogue, resource-grant checks and flush decisions. Neither crate opens databases, Kafka, ClickHouse or network connections.

OTLP uses the existing generated `opentelemetry-proto` 0.33.1 types, not a second handwritten OTLP input model. `projection::project` converts a validated original observation into generated analytical fields matching SQL columns. Resource/scope presence, schema URLs, metric description/metadata, dropped-attribute counts, exemplars, histogram structures and original attribute order survive. Unknown Protobuf fields discarded by the existing decoder are not preserved. Dictionary-indexed profile attributes are not admitted as metrics attributes.

The only normalized Kafka encoding is **one bare Protobuf `AnalyticalPoint` per record**, consumed by ClickHouse **26.8.34.13** with `ProtobufSingle`. `projection::serialize` emits no outer length prefix or batch envelope. There is no JSON normalized runtime format, hex payload, registry envelope or alternate Kafka reader. No schema registry, extra storage process or Java/Keeper dependency is required.

### Binary mapping and schema deployment

The [pinned parser](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Processors/Formats/Impl/ProtobufRowInputFormat.cpp) distinguishes `Protobuf` (a delimited stream) from [`ProtobufSingle`](https://clickhouse.com/docs/interfaces/formats/ProtobufSingle) (one bare message). Kafka uses only `ProtobufSingle`. The multirow file/HTTP fixtures and query exports use the standard `Protobuf` stream format, with explicit length-delimited file serialization; this is not a second Kafka contract or compatibility reader. Cloud support is not claimed.

The generated analytical message exists because a typed point table needs one observation per row with explicit scalar/distribution/attribute columns, rather than an opaque embedded hierarchical OTLP request. It is a SQL projection of generated OTLP, not an alternative collector protocol. Proto3 `optional` maps to `Nullable`: absent is NULL, while present `0`, `false`, empty string or empty bytes remain present. The pinned [nullable serializer](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Formats/ProtobufSerializer.cpp) and full ClickHouse round trip verify those distinctions; no Google-wrapper or oneof-presence workaround is needed.

Strict normalized validation compares optional scalar Float64 bits as well as generated shape/value equality, so changing `-0.0` to `+0.0` against unchanged singleton OTLP is rejected. The ClickHouse round trip explicitly checks scalar bits, including a generated OTLP oneof `-0.0` projected through optional Protobuf. Other Float64 fields use generated value equality in that round-trip check; it is not an exhaustive bitwise proof for all attribute/distribution floats.

Build-time Prost/protoc generation emits both Rust messages and a descriptor. The small generator in [`build.rs`](../crates/telemetry-schema/build.rs) derives `ANALYTICAL_COLUMNS` from the `AnalyticalPoint`/`AttributeNode` descriptors: primitive widths, repeated arrays, named tuples and optional nullable slots. The SQL fixture substitutes these generated columns; it does not maintain an independent field list. Enums/booleans map to UInt8, native bytes to String, and the two 32-byte digests to FixedString(32). Changes to the authoritative schema must update the explicit OTLP projection and semantic fixtures together.

Deployment must distribute the **same `recount.proto`** to every ClickHouse consumer under its configured `format_schema_path`. Use `kafka_format='ProtobufSingle'`, `kafka_schema='recount.proto:AnalyticalPoint'`, no schema-registry prefix, and disable autogenerated schemas. The exporter retains generated transport settings and bundle provenance; its manifest records `kafka_format` and `point_rows=1`. The existing descriptor can be reused when its content is unchanged. Validate generated columns and schema artifact hashes before cutover; do not add old readers or migrate discarded prototype data. Build tooling requires pinned Prost/code-generation dependencies; no runtime generator or schema service is introduced.

## Security, source and resources

| Identity          | Meaning and rule                                                                                                                                                                                                                                                 |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Project           | Trusted security and data-management scope; not a mandatory cluster type.                                                                                                                                                                                        |
| Source            | Stable authenticated exporter/collector/gateway principal within the project. Credential rotation must preserve it. A credential ID is not a source ID or hash input.                                                                                            |
| Observed resource | Project-qualified enrolled root, explicitly bound independent resource or deterministic supported root-local identity. Kinds include unknown, host, CPU, GPU, process, VM, container, gateway and sensor. No mandatory parent, boot ID, PID or fixed-depth tree. |
| Stream            | Source/resource, canonical resource/scope/point attributes, instrumentation name/version, schema URLs, metric name/unit/kind, temporality/monotonic semantics and start time.                                                                                    |
| Continuity        | Optional `recount.counter.segment_id`, retained separately and included through point attributes in stream identity. Unknown stays unknown; start time zero is preserved.                                                                                        |
| Sample            | Immutable original observation position in a named submission; independent of stream enrichment, receipts and output batching.                                                                                                                                   |

`ResourceContext` carries the resolved reference and generated `ResourceAccess`: `Root`, `Local { root_id, adapter, local_incarnation }` or `Bound`. Root/Bound use the existing resource ID; there is no separate binding ID. Topology, host/device references and relationships remain optional. Standard node-bound input can omit Linux metadata and use its authoritative enrolled root. Supported adapters can identify local resources without enrolling each PID/core/GPU separately; an omitted or ambiguous identity is never invented from array position.

`metadata::resource_claim` parses optional `recount.resource.id`/`recount.resource.kind` attributes as claims, never authority. The selected trusted adapter resolves local claims into typed context using its enrollment policy. An explicit independent resource ID requires exact binding membership. Host/device promotion is adapter-owned and project-qualified; display names and parent/placement assertions are not resource grants or physical-ownership evidence.

Relationships carry typed endpoints, kind, optional effective interval, explicit evidence and provenance. Containment, placement, allocation and observed-by are distinct. Missing effective times do not mean “valid forever”; provenance is a source claim, not independent verification. Relationship assertions do not establish delegation or workload attribution. VM placement is demonstrated in fixtures; missing sensor topology remains absent. These fields are hooks for supported adapters, not an inventory service, scheduler-allocation model or generic relationship parser. Source-provided relationship attributes are preserved even when an adapter does not interpret them.

### Resource-grant interface

1. Authenticate each request against the authoritative credential database, including project/source binding, revocation, expiry and admitted signal/profile. Fail closed on authority outages. Keep bounded pooled/indexed reads; no credential cache or offline-token feature is selected.
2. Resolve one context per original `ResourceMetrics`. `policy::requested_authorities(raw, max_distinct)` collects distinct root IDs and independent resource IDs, not local PID/core/device IDs. Fetch only those bounded indexed authority keys after credential authentication.
3. Supply trusted `RootGrant { security, root, adapter, allowed_local_kinds }` and `BoundGrant { security, resource }` snapshots to `policy::authorize`. Root includes its enrolled ID/kind. The checker requires exactly the requested authority keys, matching project/source and typed independent/root references. A root grant permits only its explicit adapter/local-kind set; an empty kind set grants the root alone, never a wildcard. No per-point or per-local-resource database lookup, full-fleet scan or payload-derived delegation is needed.
4. Supported local kinds are CPU, GPU, process, container and sensor, further restricted by the trusted adapter grant. `identity::local_resource_id` hashes domain `recount.local-resource`, project, stable root ID, kind and stable local incarnation with the existing typed length-prefix hashing. Its reserved `recount.local.` namespace cannot be used as an enrolled root or independent binding. Source is bound separately, so credential rotation does not alter local identity. Local tokens must distinguish adapter-local incarnations; they are not attestations of physical ownership.
5. VM and other independently identified/movable devices use explicit stable Root/Bound identities, not a hash of their current physical host/gateway. A VM can itself be an enrolled root for its local resources. Root-local GPU/sensor identities are local observations, not claims to an independently enrolled device with the same displayed identifier. Claiming a different root, an ungranted adapter/kind or an unbound independent ID fails closed.
6. Store checked project/source, resource identity and `ResourceAccess` in raw context and normalized lineage. `policy::validate_context` verifies deterministic identity/shape on replay without refreshing credentials, topology or the current grant policy. Resolve immutable retries consistently; never replace their identity from later placement enrichment.

The application persists tenant-qualified grants in `ingestion.collector_root_grant` and `ingestion.collector_resource_grant`. Credential creation writes the credential and its grants atomically. The ingestion API reads only the bounded requested authority keys through its SELECT-only PostgreSQL role. Grant-set construction remains a trusted service responsibility; the pure checker cannot authenticate a fabricated set or attest measurement truth. Credential checks happen on every submission, including retries. A legitimately accepted record can finish processing after later revocation or policy changes. The normalizer does not reauthorize against current credentials or human memberships. Private readers independently authorize project access before querying.

## Sample identity and retry rules

`sample_id` is SHA-256 over length-prefixed typed fields: domain `recount.sample`, trusted project, trusted source, payload-kind UInt64, identity discriminator `client` or `record`, identity token, then the original resource/scope/metric/point indexes as UInt64. Lengths and integers are unsigned 64-bit big-endian. The [cross-language vector](../tests/fixtures/telemetry/identity.json) fixes the expected digest. Sample hashes never include attributes, topology, credential IDs, receipt time/UUID, Kafka offsets or normalizer batch boundaries.

With `recount-batch-id`, the identity token is the immutable client batch ID. Without it, the trusted server record ID protects replay of that Kafka record only. Independent third-party submissions can duplicate observations; content similarity does not grant stronger deduplication. UUIDs are acceptable client tokens, but the contract accepts 1–128 ASCII alphanumeric/`-`/`_` bytes. Tokens are project/source/payload-kind scoped, not secret credentials.

`recount-batch-created-unix-nano` is a positive decimal UInt64 and is required together with the batch ID. Metadata keys must not repeat. `recount-collection-profile` is absent/`standard` for ordinary authorized OTLP or `linux` for the Recount collector adapter; `linux` requires durable batch identity. Recount credentials use prefix `recount_`. These are current owned names, with no old aliases.

The producer assigns identity **after** splitting a new batch and durably retains body order, values, times and metadata across retries. Reusing an ID with changed content is a protocol violation. There is no permanent conflict registry, first-content-wins rule or promise that all conflicts are detected. Such violations have undefined competing-row results. A changed original position is a different sample, even at the same time/metric. Worker regrouping must retain the stored original positions and IDs; it must never enumerate output rows to generate new identities.

`metadata::age(batch, received, maximum_age_ns, skew_ns)` accepts explicit per-source UInt64 nanosecond policy: positive maximum age `R`, non-negative skew `S`, and a non-overflowing `R + S`. Zero skew means no future creation-time tolerance. There are no shared 24-hour/one-hour ceilings. Reject batch creation more than `S` ahead or more than `R + S` behind receipt; the application owner must wire authorized source policy and align the collector queue lifetime with it.

That check requires declared batch creation metadata. Standard OTLP without the optional batch extension remains supported; measurement time must not be substituted for an unknown submission creation time.

Measurement event/start times remain unchanged and separate from submission age. Existing structural checks require nonzero event time and start ≤ event; there is no blanket measurement-age/future cutoff. The fixture admits a three-day-old upload under a seven-day policy with a much older measurement and replays its accepted record after submission expiry. Never apply current source age/revocation to accepted Kafka replay. Partition fanout/backfill feasibility belongs in native integration tests; escalate an actual incompatibility before proposing admission restrictions. Upload age, broker retention and recovery windows are different controls.

## Routing, batching and acknowledgement

| Boundary         | Rule                                                                                                                                                                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Raw Kafka        | `recount.metrics.raw`, Protobuf `RawRecord`; one bounded original request per record. Key is domain-separated `recount.raw-route` over the immutable sample seed at zero original position. Different batch IDs spread even one busy gateway across shared partitions.                                 |
| Normalizer       | Group `recount-normalizer`. Decode/revalidate raw shape, semantics, bindings and expansion. Publish every normalized record with confirmed acknowledgement before completing that input record. Commit only a contiguous completed prefix per raw partition.                                           |
| Normalized Kafka | `recount.metrics.normalized`, one bare `AnalyticalPoint` per record. Stream SHA-256 chooses the explicit shared partition: first eight digest bytes as big-endian UInt64 modulo the fixed partition count. `point::kafka_records` serializes and routes each point independently under the byte bound. |
| ClickHouse       | Group `recount-clickhouse`. Native Kafka table → non-aggregating MV → replacing point table. Storage precedes downstream offset advancement under the pinned server's configured settings; storage and Kafka offsets are not transactional.                                                            |

Validate the **whole request**, including exact normalized output-size preflight, before publishing raw Kafka. Return the standard empty OTLP success response only after raw publication acknowledgement. A publication timeout may be ambiguous; retry unchanged. Authenticated empty requests may succeed after authority checks without publication. There is no partial OTLP success in this contract.

Oversized raw/expanded/normalized submissions return terminal OTLP `RESOURCE_EXHAUSTED` **without `RetryInfo`**, before any raw publication. The gRPC adapter maps deterministic limit failures to that status. It does not return an infinite-retry outage response or partially accept the rows that fit.

Multi-host requests remain one bounded raw record: no ingestion-time split can silently change acknowledgement boundaries or original positions. The normalizer can publish them across several normalized partitions/messages, so partial analytical visibility is normal. Confirm all output before committing input. A crash after some/all output acknowledgement replays identical sample IDs, not a new worker-batch identity.

Routing is independent of the ClickHouse sort key. Raw requests do not promise per-resource ordering; normalized routing supplies partition affinity, not event-time order across concurrent raw partitions. Consumers/readers must handle late/out-of-order observations. The initial operational policy holds partition counts fixed for affinity; it is not a permanent product limit. Resizing requires an explicit coordinated routing/ordering policy rather than assuming arbitrary count changes preserve order. Do not silently use a different default partitioner.

The pinned [KafkaSource](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/KafkaSource.cpp) supplies complete Kafka records to the format executor. The normalizer emits one point and the selected `ProtobufSingle` parser consumes one message. Require `kafka_schema_registry_skip_bytes=0`, `kafka_skip_broken_messages=0`, `kafka_handle_error_mode='default'`, zero input-format error tolerance, `kafka_commit_every_batch=0` and no direct-query commits. With native poll batch and row target 1, each supported message touches one event-day partition; the generated profile retains a finite conservative insertion-partition ceiling. It is not a normalizer packing option. Native polling, offsets, sparse flush and durability require the real Kafka/MV gate.

## SQL projection and replacement

The executable [DDL and query fixture](../tests/telemetry-pipeline/contract.sql) is the exact format/type mapping, not production DDL. It exercises a non-aggregating MV and `ReplacingMergeTree` without a running broker.

| Projection               | SQL representation                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Query identity           | String project/source/resource, UInt8 resource kind, nullable String host/device, metric name/unit, UInt8 kind, scope name/version and schema URLs.                                                                                                                                                                                                                                                            |
| Original sample / stream | Native 32-byte SHA-256 in `FixedString(32)`; full sample ID ends the replacement key. Use `hex` only for diagnostics/text boundaries.                                                                                                                                                                                                                                                                          |
| Time / partition         | Native UInt64 event/start nanoseconds. `event_day = floor(event_ns / 86400000000000)` as UInt32; no DateTime64 or signed timestamp conversion. Full UInt64 range is retained.                                                                                                                                                                                                                                  |
| Scalar                   | `Nullable(Int64)` and `Nullable(Float64)` are separate. Zero differs from missing. A missing scalar requires no-recorded flag bit 1; flags are preserved and readers exclude no-recorded values even if payload value exists.                                                                                                                                                                                  |
| Semantics                | UInt8 metric kind/temporality, nullable UInt8 monotonic, nullable continuity string. Gauge/summary temporality is 0; only sums have monotonic state.                                                                                                                                                                                                                                                           |
| Histogram                | Nullable UInt64 count; nullable Float64 sum/min/max; Float64 explicit-bounds array and UInt64 bucket-count array. Count is present for each histogram; absence of optional sum/min/max is retained. Empty distributions are permitted under OTLP shape rules.                                                                                                                                                  |
| Exponential histogram    | The same count/statistics; nullable Int32 scale, UInt64 zero count, Float64 zero threshold; nullable Int32 positive/negative offsets plus UInt64 count arrays. Null offset means absent buckets; offset zero plus empty array means present empty buckets. Scale is retained without invented protocol range restrictions.                                                                                     |
| Summary                  | UInt64 count, Float64 sum and parallel Float64 quantile/value arrays. Nullable shared columns distinguish other metric kinds; summary count/sum themselves are present.                                                                                                                                                                                                                                        |
| Attributes               | Resource/scope/point attributes and metric metadata each use a typed flattened-tree array described below, not binary-only fields.                                                                                                                                                                                                                                                                             |
| Supported evidence       | Description and dropped counts have native columns. `exemplars` and `resource_entity_refs` are arrays of binary existing generated OTLP messages. `lineage` contains original position, batch/receipt metadata, payload kind, resolved root/local/bound scope and relationships. These structures remain lossless without a complete point copy. Entity references/relationships are not enrollment authority. |

Protobuf retains native signed integers, UInt64 time/counts, doubles and byte strings. No integer attribute, count or nanosecond timestamp passes through Float64 or a JavaScript number. Recount's current application policy rejects nonfinite values, including attributes/exemplars/distributions; that is not a claim that all such values are universally invalid OTLP. Text/browser integrations still require explicit exact-integer serialization independently of this Kafka encoding.

Attribute rows are generated named SQL tuples `(path String, kind UInt8, string_value Nullable(String), int_value Nullable(Int64), double_value Nullable(Float64), bool_value Nullable(UInt8), bytes_value Nullable(String))`. Paths use JSON Pointer escaping (`~0`, `~1`), with decimal indexes for array children; that path convention does not make the encoding JSON. Kind tags distinguish absent `KeyValue.value` (0), empty `AnyValue` (1), string (2), integer (3), double (4), boolean (5), bytes (6), array (7), key/value list (8). Containers get their own row. Original depth-first array order preserves original map/array order and empty containers; parent kind disambiguates map key `"0"` from array index `0`. Duplicated map keys are rejected recursively. Canonical identity hashing independently sorts map keys while preserving array order/numeric types/Float64 bits. SQL filtering uses named tuple paths/kinds and native value slots, including nested attributes.

The target partitions by **event day**, never receipt or processing time. Its sort/replacement key is `(project_id, source_id, resource_id, metric_name, time_unix_nano, sample_id)`. Resource ID is the immutable observed reference, not host display name, topology path or gateway placement. Event partition and sort fields must remain fixed for immutable retries. Do not replace this with a batch-minute key: that would discard distinct observations.

Replacing merges are physical cleanup, not an immediate uniqueness boundary. Ordinary reads can contain retries. Duplicate-sensitive calculations must first select logical unique samples (`FINAL` in the fixture, or a separately proven exact identity-grouping query). Then apply project/resource/metric/time filtering and calculation. Background merge completion must not change the answer. Do not group by timestamp/value alone or assert whole-batch visibility. Counter calculations additionally require matching continuity, increasing time and source semantics; rate/rollup products are outside this gate.

## Validation, limits and failure handling

The pure implementation and fixtures retain these approved **provisional configurable** defaults. Later adapter wiring and integration validation remain necessary; these are bounded-work controls, not deployed admission policy or capacity guarantees:

| Bound                                      | Value                                                                                                                                                          |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decoded request and complete raw envelope  | 4 MiB each; envelope overhead can lower the largest admissible OTLP request.                                                                                   |
| Original observations                      | 16,384 per request.                                                                                                                                            |
| Expanded decoded work                      | 262,144 resource/scope/metric containers, observations, buckets, bounds, quantiles and exemplars per request; empty containers count too.                      |
| Distinct roots and independent bindings    | 256 combined request authority keys; local resource count does not multiply enrollment or database queries. Not a project/node-count limit.                    |
| Attributes                                 | 128 recursively counted value nodes per resource/scope/point/metadata/exemplar set; nesting ≤16; keys ≤128 bytes; individual string/byte values ≤65,536 bytes. |
| Normalized row / Kafka record              | 1 MiB bare Protobuf bytes for exactly one point.                                                                                                               |
| Complete normalized output per raw request | 16 MiB total bare point-message bytes, measured by the exact shared serializer before acceptance.                                                              |

`Limits` is passed explicitly to shared validators. `Limits::validate` rejects zero bounds and normalized record bytes greater than total output bytes. Decoded bytes, points, expanded items, distinct authorities, recursive attribute-node count and normalized record/total bytes are configurable fields. Key length 128, depth 16, individual attribute value bytes 65,536 and other identifier/metric/relationship length guards are current implementation constants, **not existing configuration knobs or permanent product limits**. Later adapter configuration must make any changes coherent across validation, hashing and projection; no per-helper CLI/settings framework is introduced here.

`expanded_items` charges each `ResourceMetrics`, `ScopeMetrics` and `Metric` before validating its contents, even with no observations. The returned point count still counts observations only. This bounds decoded semantic work, not allocations Prost already performed; `encoded_len()` also remains a linear traversal before the semantic budget loop. The API's supported pre-decode admission/concurrency guard must bound simultaneous decoding. No custom Protobuf scanner/parser or peak-memory proof follows from this post-decode check.

After request validation, normalization builds one bounded position-indexed binding-reference vector and validates count, range and uniqueness. Lookup is linear overall in resource/binding count rather than a repeated whole-binding scan. Binding array order does not change original resource positions or sample identity. Point enumeration remains one linear pass per metric per validation/normalization stage; singleton extraction clones only the selected observation, and analytical projection decodes that singleton rather than scanning the original whole metric again.

Per-point resource/scope context still repeats because every stored point is independently queryable; no context registry/dictionary service is introduced. Binary encoding removes textual integer/hex expansion and avoids complete-envelope duplication, but does not make repeated large metadata free. The repeated-65,536-byte fixture admits 45 rows within bounds and rejects the 256-repeat case before acceptance. Normalization stops incrementally at the output limit rather than accumulating the entire rejected output. Recursive attribute limits bound flattened path expansion and temporary work. The defaults remain provisional safety caps, not a justified HPC workload/storage budget.

Admission preflight and final publication both use `projection::encode`/`serialize`; there is no handwritten size estimator. They measure actual bare messages, including their nested-message envelopes but no outer row length. Raw size includes the trusted envelope, not just OTLP payload. Fixtures retain exact-size minus one, exact-size and exact-size plus one assertions for raw bodies, point records and total output, and verify one routed record per point. Multibyte text, quotes, backslashes and newlines survive as native strings. Transport adapters enforce decoded byte limits before decoding, including fields the decoder would discard.

“Total output” means logical bare point bytes emitted **once for one accepted raw record**, not Kafka framing/headers, publication attempts, retry traffic or every independently accepted resend combined. Broker limits include their own overhead separately.

The ordinary CPU/process fixture is **831 raw / 1,617 bare Protobuf bytes**; its saved JSON comparison was 823 raw / 8,803 JSON bytes. The heavy fixture is **68,288 raw / 2,714,863 bare Protobuf bytes**, dominated by 2,687,755 bytes of repeated resource attributes; the saved JSON comparison was 68,268 raw / 8,193,323 JSON bytes. Current raw context includes resolved authority provenance. These uncompressed sizes are not throughput, CPU, memory or workload-capacity measurements. Saved JSON sizes are comparison evidence, not another runtime codec.

The 16 MiB bound is **not a peak-memory bound**. A call also holds raw bytes, a decoded request, the growing internal point vector, one decoded singleton/context, an analytical projection and its binary buffer. There is no JSON tree or hex buffer, but an oversized row is still projected/encoded before rejection. The implementation reuses the already decoded request. A global ingestion permit spans decoding, validation and publication, including cancelled blocking work. The normalizer bounds active work and derives fetch/producer queues from configured record ceilings. These controls and resource-limited fixture runs do not establish worst-case decoder allocation, allocator overhead, CPU cost or a production per-request budget. Ingestion preflight intentionally pays projection/serialization cost before acceptance; the normalizer repeats it after retained-boundary validation.

Collector, ingestion API, broker, normalizer and ClickHouse settings must be coherent: collector payloads fit the API's resolved raw envelope; ingestion and normalizer share current structural/output limits; broker record/fetch capacity covers configured body limits plus overhead; ClickHouse parsing/block/flush settings cover those records. Validate ordinary configuration and matching schema/DDL with integration tests, not a custom drift controller or registry. Lowering downstream limits under an accepted backlog needs explicit disposition. Bound all in-flight decoded/temporary work and concurrency; these fixtures do not size a fleet.

`policy::FlushLimits` remains a pure helper for batching adapters. The normalizer does not buffer points for a row-fill target: after whole-input validation it publishes each point directly. Native ClickHouse sparse-flush timing remains a separate integration assertion.

| Category                                  | Boundary behavior                                                                                                                                                    |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Invalid / Unsupported / Forbidden / Limit | Reject the whole submission before raw publication. Service adapters choose safe gRPC statuses; no submitted values/secrets appear in shared error text.             |
| Expired                                   | Terminal submission rejection or explicit local pending-buffer expiry, never silent deletion of accepted replay.                                                     |
| Poison                                    | Deterministic retained-record failure takes explicit global handler fail-stop; unfinished input remains unsettled. No skip, quarantine or delayed-copy policy.       |
| Outage                                    | Native producer retries are bounded by delivery timeout, then handler failure stops the app. Native consumption errors can remain logged while running.              |
| RetentionGap                              | Initial snapshots reject unavailable checkpoints. Later native errors remain logged with reset=`error`; no automatic suffix selection or promised health transition. |

`validate::request` applies shared structural checks and current Recount application policy to standard OTLP without a name allowlist. `validate::raw` adds retained-context/identity and exact output checks; it does **not** authenticate credentials or retrieve grants. `policy::authorize` must run at admission with the trusted request snapshot. `validate::retained_raw` checks deterministic accepted shape without current grant/age refresh and categorizes failures as poison. `validate::normalized` checks supported OTLP and derived fields/identity again. Generated shape safety never substitutes for actual-boundary semantic and authority checks.

The catalogue covers Recount-owned collector metrics and explicitly listed standard/vendor mappings. `catalogue::validate_collector_metric` is opt-in adapter policy; never invoke it as a global allowlist for authorized application/IoT OTLP. Linux boot/process metadata requirements stay in the Linux adapter. DCGM samples are native-time gauge ratios or `By/s` rates, not counters; cached repeated timestamps are possible. No GPU hardware/MIG or workload-attribution guarantee is made.

## Validation boundaries

The [Rust fixture](../tests/fixtures/telemetry/cases.rs) covers every admitted kind, signed limits, UInt64 time/count limits, missing/no-recorded values, structured typed attributes, optional distributions, instrumentation/schema URLs, native GPU time, VM placement, multiple sensor resources, incomplete topology, continuity changes, retry identity, receipt independence, explicit grants and expansion rejection. The SQL fixture checks native typed projections, selective project/resource/metric/time queries and duplicate-sensitive results before replacing cleanup.

Run ordinary Rust contracts natively, including the schema exporter's unit tests. The real storage suite uses the host-built `contract_fixture` executable, the reused Kafka/ClickHouse backend, disposable databases and fresh topic/group namespaces. It checks the native Kafka/materialized-view path, all projected fields and scalar Float64 bits through Protobuf, exact values and logical uniqueness. See the [test contract](../tests/README.md) for required synthetic allocation settings:

```sh
cargo test --locked --workspace --all-targets
cargo build --locked -p recount-telemetry-validation --example contract_fixture \
  --message-format=json
just test-integration storage
```

Set `RECOUNT_CONTRACT_FIXTURE` to the executable path reported by Cargo. On Linux, Cargo also executes the collector's Linux-only sampling/export tests. Other hosts can cross-build Linux harnesses on the host and pass their compiler-artifact JSON to the optional resource-limited runner; it does not compile application sources or start backends:

```sh
mkdir -p .state/contract
cargo test --locked --workspace --all-targets --no-run --message-format=json \
  > .state/contract/linux-build.jsonl
just test-linux .state/contract/linux-build.jsonl
```

That build command assumes a Linux host, or a Linux target/cross-toolchain selected by the invoking environment. The runner detects AMD64 or ARM64 from ELF headers, rejects mixed architectures and executes harnesses in its pinned Bun runtime image without network access. Supply artifacts compatible with that image's libc. Compiler, target-directory and tool installation configuration remain outside the runner.
