# Telemetry point contract

Recount metrics use authenticated OTLP input, raw Kafka retention, a Rust normalizer, normalized Kafka records and native ClickHouse point ingestion. PostgreSQL supplies credential and application authority only. Partial and eventual chart visibility are accepted; Kafka acknowledgement does not promise queryability.

The collector, ingestion API, normalizer, native ClickHouse consumer and authorized readers use this contract. PostgreSQL stores current credential/root/resource grants and application metadata, not telemetry acceptance or completeness manifests. No discarded prototype format is supported alongside it.

The ingestion API performs exact normalized-output preflight before raw Kafka publication. The normalizer revalidates retained input before publishing analytical rows. The 1 MiB normalized row/record and 16 MiB total-output defaults are provisional configurable safety values, not production capacity guarantees.

## Authoritative types and boundaries

[`recount.proto`](../crates/telemetry-schema/proto/recount.proto) generates `RawRecord`, the normalized wire projection `AnalyticalPoint`, security/resource references and original positions. [`recount-telemetry-schema`](../crates/telemetry-schema) owns those types, canonical hashing, bounded normalization and the shared ClickHouse schema renderer. [`recount-telemetry-validation`](../crates/telemetry-validation) owns pure semantic checks, metadata parsing, the adapter catalogue, Linux identity parsing and resource-grant checks. Neither crate opens databases, Kafka, ClickHouse or network connections.

OTLP uses the existing generated `opentelemetry-proto` 0.33.1 types, not a second handwritten OTLP input model. `point::normalize_bounded` lowers validated original observations directly into generated analytical fields matching SQL columns. No intermediate point message or encoded OTLP fragment is needed. Resource/scope presence, schema URLs, metric description/metadata, dropped-attribute counts, exemplars, histogram structures and original attribute order survive. Unknown Protobuf fields discarded by the existing decoder are not preserved. Dictionary-indexed profile attributes are not admitted as metrics attributes.

`RawRecord.delivery` distinguishes collector-reported connection/interface observations from the ingestion API's socket peer address. Collector binary metadata is limited to 4096 bytes, 32 interfaces and 32 addresses per interface, with explicit inventory status and truncation. Standard OTLP senders need not supply it. Duplicate, malformed or oversized diagnostics fail admission; retained replay checks the same bounds without inspecting current network state. `PointLineage.delivery` keeps connection timestamps, socket addresses, hostname and matching-interface context rather than repeating the full inventory on every point. The full observation lives in raw Kafka retention. Forwarded-address headers are ignored. These fields neither grant access nor enter sample or stream identity; queued payloads remain immutable across retries. See [export and privacy](../apps/collector/README.md#export-and-privacy) for collection scope and privacy.

Recent Kafka records carry length-delimited `AnalyticalPoint` messages, consumed by ClickHouse **26.8.34.13** with `Protobuf`. Late Kafka records carry one bare point per record, consumed with `ProtobufSingle`. `projection::serialize` emits the bare point before the normalizer selects the lane and framing. No schema registry or extra storage process is required.

### Binary mapping and schema deployment

The [pinned parser](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Processors/Formats/Impl/ProtobufRowInputFormat.cpp) distinguishes `Protobuf` (a delimited stream) from [`ProtobufSingle`](https://clickhouse.com/docs/interfaces/formats/ProtobufSingle) (one bare message). Each Kafka topic has one encoding; file/HTTP fixtures and query exports use length-delimited `Protobuf`. Cloud support is not claimed.

The generated analytical message exists because a typed point table needs one observation per row with explicit scalar/distribution/attribute columns, rather than an opaque embedded hierarchical OTLP request. It is a SQL projection of generated OTLP, not an alternative collector protocol. Proto3 `optional` maps to `Nullable`: absent is NULL, while present `0`, `false`, empty string or empty bytes remain present. The pinned [nullable serializer](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Formats/ProtobufSerializer.cpp) and full ClickHouse round trip verify those distinctions; no Google-wrapper or oneof-presence workaround is needed.

Lowering preserves optional and oneof Float64 bits, including scalar `-0.0`. Non-optional OTLP float defaults follow generated Protobuf encoding: either signed zero decodes as the `+0.0` default. Admission preflight and retained replay produce identical analytical bytes under these rules. Known wire vectors and the ClickHouse round trip explicitly check scalar bits. Other Float64 fields use generated value equality in that round-trip check; it is not an exhaustive bitwise proof for all attribute/distribution floats.

Build-time Prost/protoc generation emits both Rust messages and a descriptor. The small generator in [`build.rs`](../crates/telemetry-schema/build.rs) derives `ANALYTICAL_COLUMNS` from the `AnalyticalPoint`/`AttributeNode` descriptors: primitive widths, repeated arrays, named tuples and optional nullable slots. The SQL fixture substitutes these generated columns; it does not maintain an independent field list. Enums/booleans map to UInt8, native bytes to String, and the two 32-byte digests to FixedString(32). Changes to the authoritative schema must update the explicit OTLP projection and semantic fixtures together.

Deployment must distribute the **same `recount.proto`** to every ClickHouse consumer under its configured `format_schema_path`. Use `kafka_schema='recount.proto:AnalyticalPoint'`, no schema-registry prefix and no autogenerated schemas. The exporter records both lane formats and the recent message point cap. Validate generated columns and schema artifact hashes before cutover.

Both point lanes carry stream evidence on the first frame that emits a due stream in a packet. The explicit evidence bit also records streams with no markers. The stream views write that evidence to `metric_streams`; point rows retain only the existing `stream_id`. The normalizer refreshes evidence on the same bound as series metadata after Kafka acknowledgement. No extra topic or consumer group is needed. The watermark is unchanged: the existing consumers process both views, but the views need not become visible atomically. Do not expire stream rows independently of retained points.

## Security, source and resources

| Identity          | Meaning and rule                                                                                                                                                                                                                                                 |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Project           | Trusted security and data-management scope; not a mandatory cluster type.                                                                                                                                                                                        |
| Source            | Stable authenticated exporter/collector/gateway principal within the project. For enrolled collectors it is the node ID; token renewal preserves it.                                                                                                             |
| Observed resource | Project-qualified enrolled root, explicitly bound independent resource or deterministic supported root-local identity. Kinds include unknown, host, CPU, GPU, process, VM, container, gateway and sensor. No mandatory parent, boot ID, PID or fixed-depth tree. |
| Stream            | Source/resource, canonical resource/scope/point attributes, instrumentation name/version, schema URLs, metric name/unit/kind, temporality/monotonic semantics and start time.                                                                                    |
| Continuity        | Optional `recount.counter.segment_id`, retained separately and included through point attributes in stream identity. Unknown stays unknown; start time zero is preserved.                                                                                        |
| Sample            | Immutable original observation position in a named submission; independent of stream enrichment, receipts and output batching.                                                                                                                                   |

`ResourceContext` carries the resolved reference and generated `ResourceAccess`: `Root`, `Local { root_id, adapter, local_incarnation }` or `Bound`. Root/Bound use the existing resource ID; there is no separate binding ID. Topology, host/device references and relationships remain optional. Standard node-bound input can omit Linux metadata and use its authoritative enrolled root. Supported adapters can identify local resources without enrolling each PID/core/GPU separately; an omitted or ambiguous identity is never invented from array position.

`metadata::resource_claim` parses optional `recount.resource.id`/`recount.resource.kind` attributes as claims, never authority. The selected trusted adapter resolves local claims into typed context using its enrollment policy. An explicit independent resource ID requires exact binding membership. Host/device promotion is adapter-owned and project-qualified; display names and parent/placement assertions are not resource grants or physical-ownership evidence.

Relationships carry typed endpoints, kind, optional effective interval, explicit evidence and provenance. Containment, placement, allocation and observed-by are distinct. Missing effective times do not mean “valid forever”; provenance is a source claim, not independent verification. Relationship assertions do not establish delegation or workload attribution. VM placement is demonstrated in fixtures; missing sensor topology remains absent. These fields are hooks for supported adapters, not an inventory service, scheduler-allocation model or generic relationship parser. Source-provided relationship attributes are preserved even when an adapter does not interpret them.

### Resource-grant interface

1. Authenticate each request with a node access token signed by the web application, checking signature, issuer, audience, expiry and the periodically refreshed revocation list. The token carries project/source and the node's root grant. Fail closed until the revocation list has loaded. See [collector enrollment](collector-enrollment.md).
2. Resolve one context per original `ResourceMetrics`. `policy::requested_authorities(raw, max_distinct)` collects distinct root IDs and independent resource IDs, not local PID/core/device IDs. Node tokens supply one root grant and no independent bindings.
3. Supply trusted `RootGrant { security, root, adapter, allowed_local_kinds }` and `BoundGrant { security, resource }` snapshots to `policy::authorize`. Root includes its enrolled ID/kind. The checker requires exactly the requested authority keys, matching project/source and typed independent/root references. A root grant permits only its explicit adapter/local-kind set; an empty kind set grants the root alone, never a wildcard. No per-point or per-local-resource database lookup, full-fleet scan or payload-derived delegation is needed.
4. Supported local kinds are CPU, GPU, process, container and sensor, further restricted by the trusted adapter grant. `identity::local_resource_id` hashes domain `recount.local-resource`, project, stable root ID, kind and stable local incarnation with the existing typed length-prefix hashing. Its reserved `recount.local.` namespace cannot be used as an enrolled root or independent binding. Source is bound separately, so token renewal does not alter local identity. Local tokens must distinguish adapter-local incarnations; they are not attestations of physical ownership.
5. VM and other independently identified/movable devices use explicit stable Root/Bound identities, not a hash of their current physical host/gateway. A VM can itself be an enrolled root for its local resources. Root-local GPU/sensor identities are local observations, not claims to an independently enrolled device with the same displayed identifier. Claiming a different root, an ungranted adapter/kind or an unbound independent ID fails closed.
6. Store checked project/source, resource identity and `ResourceAccess` in raw context and normalized lineage. `policy::validate_context` verifies deterministic identity/shape on replay without refreshing node state, topology or the current grant policy. Resolve immutable retries consistently; never replace their identity from later placement enrichment.

The application persists tenant-qualified enrollment keys and nodes in `ingestion.enrollment_key` and `ingestion.collector_node`, and copies a key's adapter, local kinds and upload timing into each node token. The ingestion API reads only revoked node IDs through its SELECT-only PostgreSQL role. Grant-set construction remains a trusted service responsibility; the pure checker cannot authenticate a fabricated set or attest measurement truth. Token checks happen on every submission, including retries. A legitimately accepted record can finish processing after later revocation or policy changes. The normalizer does not reauthorize against current node state or human memberships. Private readers independently authorize project access before querying.

## Sample identity and retry rules

An analytical sample is identified by `(series_id, stream_id, time_unix_nano)` within the project. This assumes one writer per stream. Rebatching, position changes and retries do not create new samples. Different dimensions or continuity segments do. The highest raw offset wins. Offsets order writes within a raw partition, not across partitions. Source routing keeps retries on the same partition while the partition count is fixed; across a resize, duplicate content is identical but receipt order is not guaranteed. There is no stored per-sample digest.

`recount-batch-id` identifies the immutable client batch for routing and provenance, not sample replacement. Without it, raw routing uses the trusted server record ID. UUIDs are acceptable client tokens, but the contract accepts 1–128 ASCII alphanumeric/`-`/`_` bytes. Tokens are project/source/payload-kind scoped, not secret credentials.

`recount-batch-created-unix-nano` is a positive decimal UInt64 and is required together with the batch ID. Metadata keys must not repeat. `recount-collection-profile` is absent/`standard` for ordinary authorized OTLP or `linux` for the Recount collector adapter; `linux` requires durable batch identity. Recount credentials use prefix `recount_`. These are current owned names, with no old aliases.

The producer assigns batch identity **after** splitting a new batch and durably retains body order, values, times and metadata across retries. Reusing a batch ID with changed content is a protocol violation; there is no permanent conflict registry. The inspector shows the original position and delivery evidence for the winning write.

`metadata::age(batch, received, maximum_age_ns, skew_ns)` accepts explicit per-source UInt64 nanosecond policy: positive maximum age `R`, non-negative skew `S`, and a non-overflowing `R + S`. Zero skew means no future creation-time tolerance. There are no shared 24-hour/one-hour ceilings. Reject batch creation more than `S` ahead or more than `R + S` behind receipt; the application owner must wire authorized source policy and align the collector queue lifetime with it.

That check requires declared batch creation metadata. Standard OTLP without the optional batch extension remains supported; measurement time must not be substituted for an unknown submission creation time.

Measurement event/start times remain unchanged and separate from submission age. Existing structural checks require nonzero event time and start ≤ event; there is no blanket measurement-age/future cutoff. The fixture admits a three-day-old upload under a seven-day policy with a much older measurement and replays its accepted record after submission expiry. Never apply current source age/revocation to accepted Kafka replay. Partition fanout/backfill feasibility belongs in native integration tests; escalate an actual incompatibility before proposing admission restrictions. Upload age, broker retention and recovery windows are different controls.

## Routing, batching and acknowledgement

| Boundary         | Rule                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Raw Kafka        | `recount.metrics.raw`, Protobuf `RawRecord`; one bounded original request per record. Key is the `recount.raw-source` SHA-256 digest of the authenticated `project_id` and `source_id`, with length delimiters. The Kafka producer assigns each source to one partition while the partition count is unchanged.                                                                      |
| Normalizer       | Group `recount-normalizer`. Decode/revalidate raw shape, semantics, bindings and expansion. Publish every normalized record with confirmed acknowledgement before completing that input record. Commit only a contiguous completed prefix per raw partition.                                                                                                                         |
| Normalized Kafka | `recount.metrics.normalized-packed` for points within 24 hours of the normalizer's clock; `recount.metrics.late` for the rest. Both lanes select a partition using the first eight bytes of the stream SHA-256 digest as a big-endian UInt64 modulo the shared partition count. Recent messages pack points from one submission and partition; late messages contain one bare point. |
| ClickHouse       | Groups `recount-clickhouse` and `recount-clickhouse-late`. One native Kafka table per topic → non-aggregating MV → the same replacing point table. Storage precedes downstream offset advancement under the pinned server's configured settings; storage and Kafka offsets are not transactional.                                                                                    |

Validate the **whole request**, including exact normalized output-size preflight, before publishing raw Kafka. Admission also rejects any point dated after the source's allowed clock skew or before its maximum submission age, both measured from receipt. Return the standard empty OTLP success response only after raw publication acknowledgement. A publication timeout may be ambiguous; retry unchanged. Authenticated empty requests may succeed after authority checks without publication. There is no partial OTLP success in this contract.

Oversized raw/expanded/normalized submissions return terminal OTLP `RESOURCE_EXHAUSTED` **without `RetryInfo`**, before any raw publication. The gRPC adapter maps deterministic limit failures to that status. It does not return an infinite-retry outage response or partially accept the rows that fit.

Multi-host requests remain one bounded raw record: no ingestion-time split can silently change acknowledgement boundaries or original positions. The normalizer can publish them across several normalized partitions/messages, so partial analytical visibility is normal. Confirm all output before committing input. A crash after some/all output acknowledgement replays identical sample IDs, not a new worker-batch identity.

Routing is independent of the ClickHouse sort key. Raw partition order is Kafka append order, not event-time or processing order. The normalizer can prepare records concurrently, and readers must handle out-of-order observations. A gateway using one authenticated source stays on one raw partition even if it submits for many resources, so watch for partition skew and hot sources. Resizing can move sources; coordinate partition-count changes rather than assuming they preserve order.

When switching from batch-based keys, pause raw publication and drain old records before switching both the ingestion API and normalizers, or move both to a fresh raw topic. The normalizer rejects retained records with the previous key; replay those with the matching old binaries. The routing change does not change sample IDs, stream IDs or normalized partition selection.

The pinned [KafkaSource](https://github.com/ClickHouse/ClickHouse/blob/v26.8.34.13-lts/src/Storages/Kafka/KafkaSource.cpp) supplies complete Kafka records to the format executor. Require `kafka_schema_registry_skip_bytes=0`, `kafka_skip_broken_messages=0`, `kafka_handle_error_mode='default'`, zero input-format error tolerance, `kafka_commit_every_batch=0` and no direct-query commits. ClickHouse combines messages into inserts without changing sampling, sample identity or stored values.

The default native source target is 64 rows, with at most 32 messages per poll and a 2000 ms flush interval. The shared renderer reduces these counts when the prepared insertion-partition limit is smaller: `block_rows=min(64,R)` and `poll_messages=min(32,R-block_rows+1)`. The pinned source checks its target after processing an already-fetched poll. With exactly one row per message, a source block therefore contains at most `block_rows+poll_messages-1` rows: 95 at the default `R=128`, and never more than R distinct event days. The non-expanding view and single consumer retain that source boundary. The finite guard still throws on excessive partition fanout; it is not a normalizer packing option or a decoded-memory limit. Polling, decoding, insertion and scheduling can extend visibility beyond the flush interval. Native batching, offsets, sparse flush and durability require the real Kafka/MV gate.

## SQL projection and replacement

The [shared schema renderer](../crates/telemetry-schema/src/ddl.rs) generates the native Kafka columns and the separate projections for `metric_points`, `metric_series` and `deliveries`. Kafka input retains Protobuf field presence; the materialized views convert it to the storage encoding. The Linux profile supplies `host_id`; storage uses `''` when it is absent. There is no analytical `device_id`.

Resource kind, metric kind, temporality, attribute kind and monotonicity use `Enum8`. Monotonicity is false (0), true (1) or unknown (2). Point scalars are plain `Int64` and `Float64` tagged with `value_kind` (`ABSENT`, `INTEGER`, `DOUBLE`). Histogram and summary statistics store zero for absent values; the `UInt16` mask `statistics_present` assigns bits 0–8 to count, sum, min, max, scale, zero count, zero threshold, positive offset and negative offset. The inspector restores absence from that mask, including the distinction between absent buckets and present empty buckets with offset zero. Continuity remains nullable: an empty string can be present.

| Projection          | SQL representation                                                                                                                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Query identity      | String project/source/resource/host, metric name/unit, scope name/version and schema URLs.                                                                                                                                      |
| Stream and delivery | Stream digest in `FixedString(32)`; delivery lookup uses the source and the consumed raw Kafka partition (`UInt32`) and offset (`UInt64`).                                                                                      |
| Time / partition    | Native UInt64 event/start nanoseconds. `event_day = floor(event_ns / 86400000000000)` as UInt32; no DateTime64 or signed timestamp conversion. Full UInt64 range is retained.                                                   |
| Scalar              | Plain integers and doubles with a value kind. Readers exclude no-recorded values even when the payload contains a value.                                                                                                        |
| Distributions       | `UInt64` counts, `Int32` exponential scale and offsets, `Float64` statistics, bounds and quantiles, and `UInt64` bucket counts.                                                                                                 |
| Attributes          | Resource/scope/point attributes and metric metadata each use a typed flattened-tree array described below, not binary-only fields.                                                                                              |
| Supported evidence  | Exemplars and entity references retain their binary OTLP messages. Points keep the original position; deliveries keep request and resolved resource evidence. Entity references and relationships are not enrollment authority. |

Protobuf retains native signed integers, UInt64 time/counts, doubles and byte strings. No integer attribute, count or nanosecond timestamp passes through Float64 or a JavaScript number. Recount's current application policy rejects nonfinite values, including attributes/exemplars/distributions; that is not a claim that all such values are universally invalid OTLP. Text/browser integrations still require explicit exact-integer serialization independently of this Kafka encoding.

Attribute rows are named tuples with a `String` path, `Enum8` kind and five nullable typed slots (string, `Int64`, `Float64`, `UInt8` boolean, binary string). Only the slot named by the kind has a value; unused slots stay null. Paths use JSON Pointer escaping (`~0`, `~1`) and decimal array indexes. Kind tags distinguish absent `KeyValue.value` (0), empty `AnyValue` (1), string (2), integer (3), double (4), boolean (5), bytes (6), array (7), key/value list (8). Containers get their own row. Depth-first array order preserves original map and array order; parent kind disambiguates map key `"0"` from array index `0`. Canonical hashing sorts map keys while preserving array order, numeric types and Float64 bits.

The target partitions by **event day**, never receipt or processing time. Its sort/replacement key is `(project_id, metric_name, series_id, time_unix_nano, stream_id)`. Readers use `FINAL` so the highest raw offset wins even before background merges.

`deliveries` is keyed by project, source, raw partition and raw offset. Each nonempty raw record emits one delivery, even if its points span partitions or both time lanes. Both lanes carry the consumed raw position, not the normalized position. Replaying the same raw record replaces the same delivery key. The delivery gives full-precision receive time and request-wide event-time bounds; the inspector shows the signed difference between receipt and each bound. Keep delivery rows for as long as any retained point references them.

The delivery references immutable `delivery_contexts` by project, source and a 32-byte SHA-256 digest. Context includes the ordered resource relationships and access scopes, and the projected collector connection. Batch identity, record ID, inventory observation time and the ingestion socket peer stay with the request. The normalizer includes the context on the existing delivery frame when due and suppresses repeats only after Kafka acknowledgement, with the series resend bound. Keep contexts for as long as their deliveries. The inspector reconstructs the evidence and reports unavailable provenance if either row is missing; the views are not atomic.

The bundle contains common receipt, batch and socket evidence plus the resolved scope and relationships for each original resource that contributed points. The inspector uses the point's receipt and the series source to locate the bundle, then restores the resource evidence and original position. A point can become visible before its bundle; the inspector reports provenance unavailable until it arrives. Admission bounds the complete evidence-carrying frame against the normalized record limit. The analytical tables do not retain losing values at the same sample key or replace raw-record integrity checks.

Replacing merges are physical cleanup, not an immediate uniqueness boundary. Ordinary reads can contain retries. Duplicate-sensitive calculations must first select logical unique samples (`FINAL` in the fixture, or a separately proven exact identity-grouping query). Then apply project/resource/metric/time filtering and calculation. Background merge completion must not change the answer. Do not group by timestamp/value alone or assert whole-batch visibility. Counter calculations additionally require matching continuity, increasing time and source semantics; rate/rollup products are outside this gate.

## Validation, limits and failure handling

The pure implementation and fixtures retain these approved **provisional configurable** defaults. Later adapter wiring and integration validation remain necessary; these are bounded-work controls, not deployed admission policy or capacity guarantees:

| Bound                                      | Value                                                                                                                                                                      |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decoded request and complete raw envelope  | 4 MiB each; envelope overhead can lower the largest admissible OTLP request.                                                                                               |
| Original observations                      | 16,384 per request.                                                                                                                                                        |
| Expanded decoded work                      | 262,144 resource/scope/metric containers, observations, buckets, bounds, quantiles and exemplars per request; empty containers count too.                                  |
| Distinct roots and independent bindings    | 256 combined request authority keys; local resource count does not multiply enrollment or database queries. Not a project/node-count limit.                                |
| Attributes                                 | 128 recursively counted value nodes per resource/scope/point/metadata/exemplar set; nesting ≤16; keys ≤128 bytes; individual string/byte values ≤65,536 bytes.             |
| Normalized row / Kafka record              | Up to 1 MiB per bare point before framing. Recent messages target 128 points and 128 KiB including delimiters; a wider valid point travels alone within the broker budget. |
| Complete normalized output per raw request | 16 MiB total bare point-message bytes, measured by the exact shared serializer before acceptance.                                                                          |

`Limits` is passed explicitly to shared validators. `Limits::validate` rejects zero bounds and normalized record bytes greater than total output bytes. Decoded bytes, points, expanded items, distinct authorities, recursive attribute-node count and normalized record/total bytes are configurable fields. Key length 128, depth 16, individual attribute value bytes 65,536 and other identifier/metric/relationship length guards are current implementation constants, **not existing configuration knobs or permanent product limits**. Later adapter configuration must make any changes coherent across validation, hashing and projection; no per-helper CLI/settings framework is introduced here.

`expanded_items` charges each `ResourceMetrics`, `ScopeMetrics` and `Metric` before validating its contents, even with no observations. The returned point count still counts observations only. This bounds decoded semantic work, not allocations Prost already performed; `encoded_len()` also remains a linear traversal before the semantic budget loop. The API's supported pre-decode admission/concurrency guard must bound simultaneous decoding. No custom Protobuf scanner/parser or peak-memory proof follows from this post-decode check.

After request validation, normalization builds one bounded position-indexed binding-reference vector and validates count, range and uniqueness. Lookup is linear overall in resource/binding count rather than a repeated whole-binding scan. Binding array order does not change original resource positions or sample identity. Resource/scope attribute projections and hash prefixes are prepared once and reused for their observations. Each original observation is lowered directly, without cloning or decoding a singleton OTLP metric.

Per-point resource/scope context still repeats because every stored point is independently queryable; no context registry/dictionary service is introduced. Binary encoding removes textual integer/hex expansion and avoids complete-envelope duplication, but does not make repeated large metadata free. The repeated-65,536-byte fixture admits 45 rows within bounds and rejects the 256-repeat case before acceptance. Normalization stops incrementally at the output limit rather than accumulating the entire rejected output. Recursive attribute limits bound flattened path expansion and temporary work. The defaults remain provisional safety caps, not a justified HPC workload/storage budget.

Admission preflight measures each analytical row with the generated Protobuf `encoded_len`; final publication uses `projection::serialize`. Both use the same generated message definition, not a handwritten size estimator. Sizes include nested-message envelopes but no outer row length. Raw size includes the trusted envelope, not just OTLP payload. Fixtures retain exact-size minus one, exact-size and exact-size plus one assertions for raw bodies, point records and total output, and verify one routed record per point. Multibyte text, quotes, backslashes and newlines survive as native strings. Transport adapters enforce decoded byte limits before decoding, including fields the decoder would discard.

“Total output” means logical bare point bytes emitted **once for one accepted raw record**, not Kafka framing/headers, publication attempts, retry traffic or every independently accepted resend combined. Broker limits include their own overhead separately.

The ordinary CPU/process fixture is **831 raw / 1,617 bare Protobuf bytes**. The heavy fixture is **68,288 raw / 2,714,863 bare Protobuf bytes**, dominated by repeated resource attributes. Raw context includes resolved authority provenance. These uncompressed fixture sizes are not throughput, CPU, memory or workload-capacity measurements.

The 16 MiB bound is **not a peak-memory bound**. A call also holds raw bytes, a decoded request, prepared resource/scope context and the growing analytical row vector; publication allocates binary buffers. There is no JSON tree, hex buffer or encoded intermediate point, but an oversized row is still projected before rejection. Admission reuses its already validated decoded body; retained replay independently decodes and validates the raw record. A global ingestion permit spans decoding, validation and publication, including cancelled blocking work. The normalizer bounds active work and derives fetch/producer queues from configured record ceilings. These controls and resource-limited fixture runs do not establish worst-case decoder allocation, allocator overhead, CPU cost or a production per-request budget. Ingestion preflight intentionally pays lowering and exact size-accounting cost before acceptance; the normalizer repeats it after retained-boundary validation.

Collector, ingestion API, broker, normalizer and ClickHouse settings must be coherent: collector payloads fit the API's resolved raw envelope; ingestion and normalizer share current structural/output limits; broker record/fetch capacity covers configured body limits plus overhead; ClickHouse parsing/block/flush settings cover those records. Validate ordinary configuration and matching schema/DDL with integration tests, not a custom drift controller or registry. Lowering downstream limits under an accepted backlog needs explicit disposition. Bound all in-flight decoded/temporary work and concurrency; these fixtures do not size a fleet.

The normalizer does not buffer points for a row-fill target: after whole-input validation it publishes each point directly. Native ClickHouse sparse-flush timing remains a separate integration assertion.

| Category                                  | Boundary behavior                                                                                                                                              |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Invalid / Unsupported / Forbidden / Limit | Reject the whole submission before raw publication. Service adapters choose safe gRPC statuses; no submitted values/secrets appear in shared error text.       |
| Expired                                   | Terminal submission rejection or explicit local pending-buffer expiry, never silent deletion of accepted replay.                                               |
| Poison                                    | Deterministic retained-record failure takes explicit global handler fail-stop; unfinished input remains unsettled. No skip, quarantine or delayed-copy policy. |
| Backend outage                            | Native producer retries are bounded by delivery timeout, then handler failure stops the app. Native consumption errors can remain logged while running.        |
| Retention gap                             | Deliberately reset to retained earliest, warn and expose gap visibility. The normalizer counts reset events. The retained suffix is not complete recovery.     |

`validate::request` applies shared structural checks and current Recount application policy to standard OTLP without a name allowlist. After authorization, `validate::preflight` checks the raw envelope and lowers the unchanged validated decoded body with exact output bounds. `validate::raw` independently decodes and validates retained input before the same lowering; it does **not** authenticate credentials or retrieve grants. `policy::authorize` must run at admission with the trusted request snapshot. `validate::retained_raw` checks deterministic accepted shape without current grant/age refresh and categorizes failures as poison. Generated shape safety never substitutes for actual-boundary semantic and authority checks.

The catalogue declares metric type, unit, value constraint and adapter applicability for Recount-owned collector metrics and listed standard/vendor mappings. Linux export and admission use `catalogue::validate_adapter_metric` with the Linux adapter, including owned GPU gauges; external DCGM fixtures select the DCGM adapter explicitly. Never apply the catalogue as a global allowlist for authorized application/IoT OTLP. Linux boot/process metadata requirements stay in the shared Linux adapter contract. GPU resources resolve through the granted host-local GPU kind using verified physical/MIG UUIDs; no GPU is enrolled individually. DCGM profiling samples are native-time gauge ratios or `By/s` rates, not counters; the collector suppresses repeated cache timestamps. ## Validation boundaries

The [Rust fixture](../tests/fixtures/telemetry/cases.rs) covers every admitted kind, signed limits, UInt64 time/count limits, missing/no-recorded values, structured typed attributes, optional distributions, instrumentation/schema URLs, native GPU time, VM placement, multiple sensor resources, incomplete topology, continuity changes, retry identity, receipt independence, explicit grants and expansion rejection. The SQL fixture checks native typed projections, selective project/resource/metric/time queries and duplicate-sensitive results before replacing cleanup.

Run ordinary Rust contracts natively, including the schema exporter's unit tests. The real storage suite uses the host-built `contract_fixture` executable, the reused Kafka/ClickHouse backend, disposable databases and fresh topic/group namespaces. It checks the native Kafka/materialized-view path, all projected fields and scalar Float64 bits through Protobuf, exact values and logical uniqueness. See the [test contract](../tests/README.md) for required synthetic allocation settings:

```sh
cargo test --locked --workspace --all-targets
cargo build --locked -p recount-telemetry-validation --example contract_fixture \
  --message-format=json
just test-integration storage
```

Set `RECOUNT_CONTRACT_FIXTURE` to the executable path reported by Cargo. On Linux, Cargo also executes the collector's Linux-only sampling/export tests. Other hosts can cross-build Linux harnesses on the host and pass their compiler-artifact JSON to the optional resource-limited runner; it does not compile application sources or start backends:

```sh
mkdir -p .state/contract
cargo test --locked --workspace --all-targets --no-run --message-format=json \
  > .state/contract/linux-build.jsonl
just test-linux .state/contract/linux-build.jsonl
```

That build command assumes a Linux host, or a Linux target/cross-toolchain selected by the invoking environment. The runner detects AMD64 or ARM64 from ELF headers, rejects mixed architectures and snapshots host-built executables into an image based on the pinned Bun runtime. It runs all harnesses in one network-isolated container, without executing through host bind mounts or compiling application sources in Docker. A bounded scratch `TMPDIR` remains separate from embedded Cargo executable paths. Supply artifacts compatible with that image's libc. Compiler, target-directory and tool installation configuration remain outside the runner. Live authority, Kafka, HTTP reader, runtime-image and recovery cases remain separate native commands.

Pure fixtures do not prove native replay/rebalance or offset ambiguity, event-partition fanout, sparse timers, service faults or browser behavior. Use the separate [native gate](../infra/README.md#validate-native-ingestion), live-authority RPC test and [protected browser gate](../tests/README.md#coordinator-owned-runtime-and-recovery-gates) for those boundaries. Passing one gate does not imply that the whole collector-to-browser path passed. No timestamp cutoff, offline authorization/cache feature or blanket topology/physical-ownership guarantee is selected.
